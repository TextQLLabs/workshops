TextQL Developer Workshop — API, MCP & Integrations

A hands-on workshop for developers and technical integrators: drive Ana programmatically through the REST API, stream responses into your apps, automate playbooks and dashboards from code, expose Ana inside Claude/Cursor/ChatGPT via MCP, and extend Ana outward with MCP tools.

AWS-workshop style: copy-paste curl/Python, checkpoints. ~2 hours.

What you'll be able to do

MODULE 1

The Chat API

Sync, SSE streaming, retrieval — the agentic loop as an endpoint.

MODULE 2

Resource APIs

Connectors, playbooks, dashboards as code; the ETL-completion trigger.

MODULE 3

Sandbox API

Warehouse data into DataFrames; your code in Ana's environment.

MODULE 4

Ana as MCP server

Warehouse answers inside Claude, Cursor, and your IDE.

MODULE 5

MCP tools

Extend Ana with Notion, GitHub, Jira — or your internal APIs.

MODULE 6

Production patterns

Identity design, timeouts, cost, testing nondeterminism.

Prerequisites

  • API key access (Settings → Configuration → API Keys; creation may be role-gated)
  • curl or Python + requests; an MCP client for Modules 4–5
  • A connected data source
API shapes follow the current reference at docs.textql.com. Python SDK: TextQLLabs/textql-python. VPC deployments substitute their own host.
Module 0

Module 0 · Keys, Bases & First Call

⏱️ 15 min

Goal: get authenticated, understand the API surface, make your first successful call.

0.1 · The API surface

SurfaceBaseStyle
v2 REST API (use this)https://app.textql.com/v2HTTP verbs, path params, JSON errors, SSE
v1 (legacy)https://app.textql.comConnect-RPC, all-POST — replaced by v2
Usage/Billing API/v1/billingACU consumption records
MCP endpoint/mcpAna as a tool in MCP clients (Module 4)

v2 conventions: GET/POST/PATCH/DELETE, IDs in paths (/v2/playbooks/{id}), query-param pagination, errors as {"error": {"code", "message"}}, SSE via text/event-stream.

0.2 · Get a key

Where to click

Settings → Configuration → API Keys

Vault it, name it for its purpose, rotate on policy. Key creation is permission-gated — if you can't create one, that's a role conversation (Admin workshop).

0.3 · First call

curl "https://app.textql.com/v2/connectors" \
  -H "Authorization: Bearer $TEXTQL_API_KEY"
You'll see: The connectors your key can reach. This is the authorization sanity-check — the API sees what your identity may see, nothing more.

0.4 · First question

curl -X POST "https://app.textql.com/v2/chats" \
  -H "Authorization: Bearer $TEXTQL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"question": "What are the top 10 customers by revenue?", "connector_ids": [ID]}'
You'll see: A synchronous, warehouse-backed answer — and a real thread in the UI, fully auditable.

Module 1

Module 1 · The Chat API

⏱️ 25 min

Goal: the workhorse endpoint, three ways — synchronous, streaming, conversational.

1.1 · Synchronous

POST /v2/chats with question + connector_ids. Blocks while Ana works — fine for scripts, wrong for UIs.

1.2 · Streaming: SSE for responsive apps

curl -X POST "https://app.textql.com/v2/chats/stream" \
  -H "Authorization: Bearer $TEXTQL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"question": "Summarize last quarter sales"}' \
  --no-buffer
You'll see: Server-sent events as Ana works — tool steps, partial output, final answer. Users watch the analysis happen instead of a spinner. A cancel endpoint exists for abandoning runs.
import requests, json
resp = requests.post(
    "https://app.textql.com/v2/chats/stream",
    headers={"Authorization": f"Bearer {KEY}"},
    json={"question": "...", "connector_ids": [CID]},
    stream=True)
for line in resp.iter_lines():
    if line.startswith(b"data:"):
        handle(json.loads(line[5:]))

1.3 · Retrieve and continue

  • GET /v2/chats/{id} — full chat with messages and assets (charts, files, dashboards)
  • GET /v2/chats?search=... — list/search with pagination
  • Follow-ups continue a chat — server-side conversation state, no prompt-stitching

1.4 · Question phrasing is product surface

Your app's API questions are playbook prompts in miniature — nobody is there to clarify:

Bad: "how are sales?"
Good: "Total closed revenue for the last complete month, compared to the prior month, as a single number plus one sentence of context."

The second returns something your UI can render predictably.

Module 2

Module 2 · Connectors, Playbooks & Dashboards via API

⏱️ 20 min

Goal: manage platform resources from code — infrastructure-as-code for everything the other workshops did in the UI.

2.1 · Connectors

  • GET /v2/connectors/types — supported types and the fields each requires (build dynamic forms from this)
  • POST /v2/connectors/test — test a config without saving — wire into CI for credential validation
  • POST / PATCH / DELETE — lifecycle
The killer pattern — credential rotation as code: secrets manager rotates → job calls test with the new credential → on pass, PATCH the connector → smoke-test via a chat call. Zero-touch rotation.

2.2 · Playbooks

  • POST /v2/playbooks/{id}/run — execute now, get the report — external schedulers (Airflow, Dagster) own timing; TextQL owns analysis
  • Deploy/undeploy from code

The ETL-completion pattern (the fix for "my playbook ran before the data loaded"): remove the playbook's schedule; the pipeline's last task calls run when the load finishes. Date-handling edge cases mostly disappear when the trigger is the data event.

# last task in your DAG
requests.post(f"https://app.textql.com/v2/playbooks/{PB_ID}/run",
              headers={"Authorization": f"Bearer {KEY}"})

2.3 · Dashboards

  • POST /v2/dashboards / stream — ask Ana to build a dashboard from code
  • GET /v2/dashboards/{id} — retrieve with assets

Use case: templated provisioning — a standard dashboard per new customer/team as part of onboarding automation.

2.4 · Agent webhooks

Feed agents accept webhook triggers — one POST with a JSON payload. The integration point for "ETL finished → agent validates the load," CI events, alert managers, anything that can send HTTP.

Module 3

Module 3 · The Sandbox API

⏱️ 15 min

Goal: drive Ana's Python sandbox directly — the environment without the conversation.

3.1 · What it is

EndpointDoes
Start / StopCreate or destroy a sandbox
StatusState, loaded DataFrames, memory usage
Load Connector DataSQL against a connector → named pandas DataFrame
ExecuteRun Python in the sandbox
UploadPut a file in the sandbox filesystem

3.2 · The flow

# 1. start
sb = post("/v2/sandbox/start")
# 2. load warehouse data as a DataFrame
post("/v2/sandbox/load", json={
  "connector_id": CID,
  "query": "SELECT region, SUM(amount) AS rev FROM orders GROUP BY region",
  "dataframe_name": "rev_by_region"})
# 3. compute
post("/v2/sandbox/execute", json={
  "code": "result = rev_by_region.sort_values('rev', ascending=False).head(3).to_dict()"})
# 4. status / results, then stop
get("/v2/sandbox/status"); post("/v2/sandbox/stop")

3.3 · Chat API vs Sandbox API

You wantUse
Ana to decide how to answerChat API — the agentic loop is the product
Deterministic code you wrote, against warehouse dataSandbox API
Both interleavedSandbox for deterministic parts; chat for analytical hops

The sandbox shines for: productionized metric computations that must be exactly your code, data-quality check suites, pre-processing before a chat.

3.4 · Hygiene

Sandboxes hold state and memory. Stop what you start — created per job, destroyed after, in a finally. The status endpoint's memory readout is your leak detector.

Module 4

Module 4 · Ana as an MCP Server

⏱️ 15 min

Goal: warehouse-backed answers inside Claude, Cursor, ChatGPT, Copilot — zero context switching.

4.1 · The endpoint and the tool

MCP endpoint: https://app.textql.com/mcp — exposing a single tool, ask_question. Natural language in; Ana runs the analysis through your connectors and Ontology; the answer comes back with a link to the full TextQL thread. Charts/dashboards/reports arrive as resource links. Same Ana, same governance, headless.

4.2 · Connect your client

Claude (web): Settings → Integrations → Add MCP Server → https://app.textql.com/mcp, name ana. Auth happens automatically on first use.

Cursor — ~/.cursor/mcp.json:

{
  "mcpServers": {
    "ana": { "url": "https://app.textql.com/mcp" }
  }
}

4.3 · Use it like you mean it

"Ask ana: what was our revenue by month for the last 6 months, and which segment drove the change?"
  • Engineering context: "ask ana whether the orders table has rows for yesterday" mid-code-review.
  • The thread link is the handoff — paste it to a teammate; they get the full analysis, charts, SQL.

4.4 · Governance notes

MCP access authenticates as you — your role, connector scope, ontology folders. Every MCP question is a real thread, visible in Observability like any other.

Module 5

Module 5 · Extending Ana with MCP Tools

⏱️ 15 min

Goal: the other direction — give Ana new tools (Notion, GitHub, Jira, your internal APIs) via MCP.

Admin-configured: MCP server config lives in Settings, gated by the mcp permission (members default to read).

5.1 · The one constraint that matters

TextQL supports HTTP/SSE-based MCP servers only — not stdio/local. The quick test on any MCP config JSON: if you see url, it works; if you see command, it's stdio and won't.

5.2 · Add a server

Where to click

Settings → MCP (admin) → add server → URL + auth per the server's docs

Once added, the server's tools are available to Ana in chats — used when a question calls for them, the same way she chooses SQL or Python.

PROMPT 
What MCP tools do you have available right now? Use the [server] tool to [simple read operation — e.g., list my Notion pages / open issues].

5.3 · Wrapping your internal API

The high-leverage move: wrap internal services (deploy status, feature flags, provisioning state) as a small HTTP MCP server. Then Ana joins operational state with warehouse data in one answer:

"Which enterprise customers are on the v2 flag but show declining usage since their migration date?" — flag state from your MCP tool, usage from the warehouse. That join is the payoff.

5.4 · Choose the right integration surface

You wantUse
Ana to query a SaaS product's data at scaleWarehouse mirror or API connector
Ana to act on / read an operational system mid-analysisMCP tool
Your app to ask Ana questionsMCP server (Module 4) or REST API (Modules 0–2)

Module 6

Module 6 · Production Patterns

⏱️ 15 min

Goal: the habits that separate a demo integration from a production one.

6.1 · Identity design

  • Service identity per system integration — dedicated key, named, minimum role.
  • Per-user identity when end users see answers — their role and RLS scope what your app shows. Proxying everyone through one privileged key is how data leaks across user boundaries.

6.2 · Errors and timeouts

  • Branch on error.code, log error.message.
  • Analytical calls are long: stream for anything user-facing; sync timeouts in minutes; org limits (SQL 180s, cell 360s) bound the server side.
  • Retry with backoff for transient failures — but never blind-retry a write without idempotency thinking.

6.3 · Cost awareness

  • Cache repeated identical questions with a TTL.
  • Aggregate — one question returning a table beats fifty returning numbers.
  • Monitor — the Usage API (/v1/billing) is your integration's meter; alert before finance does.

6.4 · Testing an AI integration

  • Contract: response shape, asset presence, thread-link validity.
  • Data correctness at the source: golden-query checks for the numbers your questions depend on.
  • Specification-grade prompts (1.4) — most "flaky AI" is under-specified questions.

6.5 · Keep the audit trail connected

Every API chat is a real thread. Log the thread ID with your application events — when a user questions a number from three weeks ago, that ID is an immediate, full answer with SQL.

Sync and streaming chat, resources as code, the sandbox, Ana in your IDE, MCP extensions, and production discipline.
