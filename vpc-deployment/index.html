Deploy TextQL in Your VPC

A workshop of short, hands-on modules for platform engineers, SREs, and infrastructure teams deploying self-hosted TextQL into their own Kubernetes cluster: choosing the deployment path deliberately, prerequisites and network allowlists, the Helm install with a production-grade values file, inference configuration (including the Bedrock specifics that generate most field issues), validation, the upgrade and secret-rotation operating rhythm, and troubleshooting with the TextQL Doctor diagnostic workflow.

Total time: about 2.5 hours of guided work — wrapped around an install that, with prerequisites cleared, lands the same day.

Scope: self-hosted VPC deployment only. Managed multi-tenant and managed single-tenant (including PrivateLink) are TextQL-operated — Module 0 covers when each is the better answer, and the Admin & Governance workshop covers everything above the infrastructure.
How this workshop works

This is an infrastructure workshop, and it's intentionally terminal-first: the hands-on steps are helm and kubectl commands and values-file edits against your own cluster — not prompts to Ana. Bring a terminal with helm and kubectl installed, cluster-admin access to the target EKS cluster, and an editor for values.yaml. Copy-paste Ana prompts appear only where you exercise the deployed platform itself (Modules 3–4).

Who this is for

  • Platform/infra engineers who own the Kubernetes cluster TextQL will run in
  • SREs who will operate, upgrade, and monitor the deployment
  • Security engineers reviewing what runs where and what egresses
  • The TextQL champion coordinating between those people and TextQL support

Module 0

Module 0 · Choose the Path Deliberately

⏱️ 15 minutes

Goal: confirm VPC self-hosting is actually your answer — against the two managed options — and inventory what you're signing up to operate.

0.1 · The three deployment paths

Managed Multi-TenantManaged Single-Tenant (+ PrivateLink)Self-Hosted VPC
Who runs itTextQLTextQL (dedicated env)You
InfrastructureShared, logically separatedDedicated compute + databaseYour Kubernetes cluster
Traffic to your dataPublic internet (TLS), fixed egress IP to allowlistAWS PrivateLink — never the public internetNever leaves your network
Data residencyAWS us-west-2FlexibleFully yours
FeaturesImmediately on releaseOn release, stability-tailoredWhen you upgrade the chart
Compliance postureSOC 2 audited, pen-tested, HIPAA/GDPRSame, plus isolationInherits your controls
Operational costNone (lowest cost)NoneKubernetes + database + upgrades + monitoring, owned by your team

0.2 · When VPC is the right answer

Self-hosting earns its operational cost when at least one of these is true:

  • Strict data residency — data and compute must stay in a specific region/account/datacenter you control
  • Air-gapped or egress-prohibited environments — policy forbids third-party cloud access to internal systems
  • Your controls must apply — your secrets manager, your network policy, your audit pipeline, as a hard requirement rather than a preference

If your actual requirement is "traffic must not cross the public internet" — Managed Single-Tenant with PrivateLink solves that without you operating Kubernetes. Queries travel the AWS backbone; no IP allowlisting; no cluster to run. Many teams that start this conversation at "VPC" land there, happily. VPC peering also exists as an alternative for orgs already running peered networks at scale.

0.3 · What you're signing up for

The honest inventory — VPC self-hosting means your team owns:

You ownWhat it means in practice
The Kubernetes clusterEKS is the tested and supported target; sizing, node pools, upgrades
The databasePostgreSQL — a managed service like RDS is the recommended pattern
Chart upgradesPatches safe to auto-apply; minor/major reviewed against the changelog (Module 5)
SecretsYour choice: AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, or sealed secrets via GitOps
Monitoring & incident responseHealth endpoints exist; the watching is yours (Modules 4–5)
First-line troubleshootingWith the TextQL Doctor workflow and support behind you (Module 6)

0.4 · The security baseline you inherit either way

All three paths share the same foundations — TLS 1.2+ in transit, AES-256-GCM at rest for connector credentials and secrets, OIDC/SSO + API key auth, per-object RBAC with org-scoped queries, and full audit logging (actor, resource, IP, auth method, timestamp). Every thread runs in an isolated, non-persistent sandbox execution environment. Self-hosting adds your perimeter around that baseline; it doesn't replace it.

Module 1

Module 1 · Prerequisites & Architecture

⏱️ 25 minutes

Goal: clear every prerequisite before install day — cluster, database, registry access, secrets backend, and the network allowlists that are always the long pole.

1.1 · The architecture at a glance

A self-hosted TextQL deployment is:

  • The application, deployed via Helm chart into your Kubernetes cluster — EKS is the tested and supported platform. Core services include the web frontend, the compute engine (Ana's brain), sandbox workers (isolated per-thread execution), and supporting services.
  • A PostgreSQL database — run it on a managed service (RDS is the canonical choice) rather than in-cluster; it holds application state, while connector credentials and secrets are encrypted at rest.
  • Outbound paths — to your data sources (entirely within your network), to your chosen LLM provider (Module 3), and to a short list of operational endpoints (1.4).

1.2 · The prerequisite checklist

Send this to the owning teams now; each row has a different owner and lead time:

PrerequisiteDetailsTypical owner
Kubernetes clusterEKS (tested/supported); cluster-admin for the install; node capacity sized with TextQL for your user countPlatform
PostgreSQLManaged instance (RDS pattern); reachable from the cluster; credentials readyPlatform / DBA
Registry accessTextQL provides a PAT token for the Docker registry — the chart pulls from registry-1.docker.io/textqllabsTextQL (request it now)
Secrets backend decisionAWS Secrets Manager / GCP Secret Manager / Azure Key Vault / sealed secrets via GitOpsSecurity
TLS + DNSA hostname for the app, certificates per your standardNetwork
IdP applicationAn OIDC app (Okta / Entra / Ping) for Module 2's single-tenant auth — issuer URL, client ID, client secretIAM team
LLM provider decisionModule 3's choice made before install day — Bedrock needs IAM work with its own lead timeSecurity + Platform

1.3 · Sizing conversation

Node capacity depends on concurrent users and sandbox workload (each active thread gets an isolated sandbox worker). Have the sizing conversation with your TextQL contact with these numbers in hand: expected total users, expected concurrent users, and whether dashboards (persistent workers) are in scope. Autoscaling node pools for sandbox workers is the pattern that absorbs spiky usage.

1.4 · Network allowlists — the long pole

Self-hosted does not mean zero egress (unless you negotiate a fully air-gapped design with TextQL). At minimum, ensure these are reachable from the VPC:

DestinationWhy
Docker Hub (registry-1.docker.io)Pulling TextQL container images — install and every upgrade
console.textql.comUsage data reporting
Your LLM provider's endpointAnthropic/OpenAI APIs, or Bedrock/Vertex endpoints in your cloud (Module 3) — unless fully self-hosted models
Any domains allowlisted in the TextQL proxySandbox operations that reach approved external services (e.g., source control for ontology sync)

File the firewall tickets now — in most organizations this row, not the Helm install, sets the project timeline.

Bonus of the VPC path: the inbound allowlisting from the SaaS world disappears. Your warehouse connectors don't need TextQL's public egress IPs allowlisted — all connector traffic stays inside your network (the Connect Your Data workshop's IP-allowlist module explicitly doesn't apply to you).

1.5 · Assemble the install bundle

Before Module 2, you should physically have: the registry PAT (from TextQL), the database connection string, the OIDC app's three values (issuer URL, client ID, client secret), your hostname + TLS material, and the LLM credentials or IAM role from Module 3's decision. Missing any one = a stalled install call.

Module 2

Module 2 · Install with Helm

⏱️ 30 minutes

Goal: the install itself — chart, values file, and the locked-down authentication configuration that should be on from day one.

2.1 · The install command

With the Module 1 bundle in hand:

helm upgrade --install <my-release> \
  oci://registry-1.docker.io/textqllabs/textql-charts \
  --version <version> \
  --values values.yaml

Registry access uses the PAT token TextQL provided. Pin an explicit --version — check the Changelog for the current release and any upgrade notes. The chart follows Semantic Versioning: that discipline matters more at upgrade time (Module 5) than install time, but start as you mean to continue.

2.2 · The values file — auth first

The single most consequential block in your values file is authentication. For an enterprise VPC deployment, the locked-down pattern is single-tenant OIDC with enforced auth:

global:
  auth:
    singleOIDCTenant: true
    singleOidcIdleLogoutAfter: "45m"          # optional idle timeout
    oidc:
      providerType: "Okta OIDC"               # Okta OIDC | Microsoft OIDC | Ping OIDC
      issuerUrl: "https://your-idp.example.com"
      clientId: "your-client-id"
      clientSecret: "your-client-secret"
      scopes: "openid profile email"          # default
      attributeMapping: '{"role_sync_enabled": true, "preserve_admin_role": true}'
      emailVerification: true                  # default
    allowedDomains: "company.com"              # optional: restrict signup domains
    banDisposableEmails: true                  # default

oathkeeper:
  enforceAuth: true

What this buys you:

  • singleOIDCTenant: true — one IdP for the whole deployment; users go straight to your IdP (the login page is bypassed); email/magic-link login is disabled; the provider shows read-only in Settings.
  • enforceAuth: true — every request must carry a valid session or API key; unauthenticated requests redirect to the IdP. This is the recommended setting for locked-down deployments — and the chart fails validation if you enable it without singleOIDCTenant, by design.
  • allowedDomains — only matching email domains can create accounts.

Two warnings worth respecting:

  • All four OIDC fields (providerType, issuerUrl, clientId, clientSecret) must be set together — partial configuration causes authentication failures, not graceful degradation.
  • Keep a break-glass access plan before you enforce auth: know how you'd correct a bad OIDC config (the values file is your recovery path — a fresh helm upgrade with corrected values).

2.3 · Role sync — provisioning without hand-assignment

With role_sync_enabled in the attribute mapping, user roles synchronize from IdP group claims on every login: group names match TextQL role names case-insensitively; matching roles are assigned; roles absent from the IdP groups are removed; unmatched groups are ignored.

The flag that prevents the classic self-inflicted lockout: preserve_admin_role: true — the admin role is never removed by sync, so an IdP group change can't strip your last admin. Set it.

One known edge: if the IdP can't return group memberships (a user in too many groups), sync is skipped with a warning — configure a groups filter in your IdP if you hit it.

2.4 · The rest of the values file

Work through with your TextQL contact for your specifics (and verify keys against the current chart version):

BlockWhat it coversNotes
DatabaseConnection to your PostgreSQLThe RDS instance from Module 1
Secrets modeplaintext vs sealedSecrets / externalSecretsProduction = encrypted modes; plaintext logs harmless "skipping encryption migration" warnings but is for dev only
Providers / inferenceLLM routingModule 3 — the whole module
Ingress / TLSHostname, certificatesYour standard
Org defaultsTool availability, feature flags, modelsRuntime-configurable in Settings too — the Admin & Governance workshop owns this layer

2.5 · First contact

After the install converges (migrations run as a pod on install — if it fails silently, that's a known issue class; Module 6):

  1. Open https://[your-hostname] — you should land on your IdP, not a login page (that's singleOIDCTenant working).
  2. Authenticate; confirm you arrive in the workspace.
  3. Check role sync: your IdP groups should map to your TextQL role.
  4. Verify in Settings that the OIDC provider shows read-only — confirmation the single-tenant mode is active.

Module 3

Module 3 · Inference Configuration

⏱️ 20 minutes

Goal: route Ana's language models per your compliance posture — direct provider APIs, in-your-cloud foundation models (Bedrock), or self-hosted open source — and avoid the Bedrock pitfalls that generate most field issues.

3.1 · The three inference postures

PostureTraffic pathWhen
Foundational model providers (Anthropic, OpenAI APIs)VPC → provider API over TLSBest model performance; DPAs in place with both providers, SOC 2 reviewed — acceptable for many compliance regimes
In-your-cloud foundation models (AWS Bedrock; similar patterns for other clouds)Stays inside your cloud accountEgress to third-party APIs prohibited; model usage billed/governed through your cloud agreement
Self-hosted open source modelsEntirely within your infrastructureAir-gapped or maximal-control postures; expect a performance gap vs leading commercial models

The decision is usually made by your security team's egress policy, not by preference — which is why Module 1 put it on the prerequisite list.

3.2 · Direct provider configuration

The simplest posture: provider API keys in your values (via your secrets backend), MODEL_PROVIDER set accordingly. One field note from real deployments: if Anthropic is your primary provider, a "failed to initialize provider: openai: missing openai key" WARN at startup is non-critical — OpenAI is only a fallback/feature path; set its key only if you want those.

3.3 · Bedrock — the configuration that rewards care

Bedrock keeps inference inside your AWS account. The Helm values → environment mapping:

global:
  providers:
    modelProvider: "anthropic"          # MODEL_PROVIDER
    anthropicProvider: "bedrock"        # ANTHROPIC_PROVIDER — routes Anthropic calls via Bedrock
    bedrock:
      globalInference: true             # BEDROCK_GLOBAL_INFERENCE
      customRoleArn: "arn:aws:iam::..." # optional — BEDROCK_ASSUME_ROLE_ARN (STS AssumeRole)
      customRoleExternalId: "..."       # optional, paired with the role ARN

When customRoleArn is absent, pods use the node/IRSA AWS identity directly — that absence is normal, not a misconfiguration.

The three Bedrock facts that prevent most field issues:

  1. Model access is opt-in per AWS account. In the Bedrock console: Model access → request access for the Anthropic models you'll use. An unenabled model fails with "The provided model identifier is invalid" — which reads like a TextQL bug and is an AWS account setting.
  2. Newer Anthropic models require inference profiles (us./eu./global. prefixed IDs), not bare model IDs. globalInference: true selects global profiles — your account must have them provisioned in-region; if not, set it false to fall back to regional profiles (which must themselves be enabled).
  3. Health checks exercise the default model. The functional health refresher tests LLM connectivity with the default model every few minutes — if that model isn't enabled in Bedrock, you'll see recurring health failures (and degraded thread-quality judging) while user chats may still work on other models. Recurring "invalid model identifier" health errors = check Bedrock model access first, app config second.

IAM-side: the EKS node role (or the assumed role) needs valid Bedrock permissions in the right region. The error "failed to refresh cached credentials" in chat points at exactly this — the IAM role attached to the EKS nodes lacking or losing Bedrock access (also in Module 6's catalog).

3.4 · Verify inference before users do

PROMPT 
Confirm which model is answering this, then run a trivial end-to-end test: query [a small table] via SQL and chart the result with Python.
You'll see: model identity plus the two execution paths (SQL, sandbox Python) exercised in one shot. Then check the deployment's functional health endpoint/monitors (Module 4) for the LLM execution check specifically — green there means the default model works, not just the one you tested.

Module 4 · Validate the Deployment

⏱️ 15 minutes

Goal: prove every subsystem works before announcing the deployment — a smoke test that exercises what the Helm install's success message doesn't.

4.1 · Pod-level sanity

kubectl get pods -n <namespace>
# everything Running/Completed; watch specifically for:
# - the DB migration pod: Completed (a silent failure here is a known issue class — Module 6)
# - sandbox-worker pods: Running, not Error/CrashLoopBackOff
# - compute-engine: Running, low restart count

Then skim startup logs for the expected warnings vs real problems — knowing the difference prevents false alarms:

Log lineVerdict
Slack bot token not provided, skipping initialization (and Teams equivalent)INFO — integration not configured; fine until you want it
missing openai key (when Anthropic is primary)WARN — fallback provider only; fine
Skipping credential encryption migration: encryption not enabledExpected only in plaintext mode — in production this line means your secrets mode isn't what you think it is
Migration pod failed, no logsReal — Module 6
Sandbox workers crashing on startup with a Python import errorReal — image/version mismatch class; Module 6

4.2 · The functional smoke test

The platform exposes functional health checks (/health/functional) covering the critical paths — LLM execution, sandbox, ontology, cache, console, web. Check them — then also prove it like a user, in a fresh thread:

  1. Auth path — log in via your IdP from a clean browser session; confirm role sync assigned the right role.
  2. The five-question connector smoke test from the Connect Your Data workshop (Module 6.1) against your first in-VPC connector — visibility, read, breadth, write-must-fail, scale.
  3. Sandbox execution:
PROMPT 
Run a quick Python test: generate 1000 random numbers, compute summary statistics, and render a histogram.
You'll see: a chart — proof the sandbox workers schedule, execute, and return artifacts. If this hangs, it's a worker/scheduling issue, not an LLM issue (the distinction matters for triage).
  1. Inference — already verified in Module 3.4; re-check the LLM health monitor is green now, post-everything.

4.3 · The restricted-user check

With a second test account holding a non-admin role: log in, confirm they see only what their role allows (connectors, settings sections). Auth working and authorization scoped are different claims — verify both before announcing. (The full access-control model: Admin & Governance, Module 2.)

4.4 · Capture the baseline

Record while everything is green: chart version, image versions, node count and types, pod resource consumption at idle, and time-to-first-token on a simple thread. This baseline is what "it got slower" gets compared against in three months — without it, every performance conversation starts from vibes.

Module 5

Module 5 · Operate: Upgrades, Secrets & Monitoring

⏱️ 25 minutes

Goal: the operating rhythm — semver-disciplined upgrades, GitOps automation, the secret-rotation gotcha, and monitoring that catches degradation before users do.

5.1 · Upgrades: the semver contract

The chart follows Semantic Versioning, which gives you a clean policy:

Version changePolicy
Patch (1.2.x)Non-breaking by contract — safe to auto-install
Minor / majorRead the Changelog first — each release documents what's new, bug fixes, and an upgrade guide section with any required steps

The manual path is the same command as install with a new --version. Two habits that keep upgrades boring:

  • Read the changelog even for patches — it's well-maintained (release notes document fixes down to specific SCIM, MCP, and storage behaviors) and 30 seconds of reading beats reverse-engineering a behavior change.
  • Re-run Module 4's smoke test after every upgrade — particularly the sandbox execution check, since worker images version alongside the chart.

5.2 · GitOps and automation

Point Flux, ArgoCD, or your CI at the TextQL registry for automatic releases. The recommended policy matches the semver contract: auto-install patches only (^1.2.x style constraints); minors and majors go through your change process with the changelog's upgrade guide in hand.

This pairs naturally with sealed-secrets-via-GitOps as the secrets mode — the whole deployment becomes a repo: values, secrets, version pin, all reviewed, all auditable, all revertible.

5.3 · The secret-rotation gotcha

The single most field-reported operational surprise: running pods do not pick up updated secret values. After rotating any secret (database password, LLM key, OIDC client secret — via kubectl edit secret, Helm upgrade, or your external secrets manager), the pods keep the old value until restarted:

kubectl rollout restart deployment/compute-engine
kubectl rollout restart deployment/web
# ...and any other deployment mounting the rotated secret

Until the restart, you get the worst failure mode: subtle auth failures that are hard to trace — the deployment looks healthy while requests fail with stale credentials. Bake the restart into your rotation runbook as a single atomic step: rotate → restart → smoke test. Never just rotate.

5.4 · Monitoring

Three layers, from platform to product:

LayerWhatHow
KubernetesPods, restarts, node pressure, PVC/storage healthYour existing cluster monitoring — TextQL is now one of your workloads
Functional health/health/functional keyword checks per subsystem: LLM execution, sandbox/code execution, ontology, cache, console, webPoint your uptime monitor (BetterStack-style keyword monitors are the reference pattern) at the endpoint; alert on subsystem failures
Product qualityThread warnings, usage, errors as users experience themThe Observability surface in-app (admin sidebar) — the Admin & Governance workshop's weekly triage loop

The functional layer is the one self-hosters skip and regret: it's what distinguishes "the pods are Running" from "Ana can actually execute a query" — recall Module 3's Bedrock case, where health checks fail while pods look perfectly healthy.

Module 6 · Troubleshooting & TextQL Doctor

⏱️ 20 minutes

Goal: triage the known field-issue classes yourself, and when you escalate, do it with the TextQL Doctor diagnostic — the workflow that turns a support cycle into a same-day answer.

6.1 · The field-issue catalog

The recurring classes from real VPC deployments, with first moves:

SymptomLikely causeFirst move
Pods stuck in ImagePullBackOffDocker registry credentials (the PAT) expiredRequest updated credentials from TextQL support; apply; restart affected pods
DB migration pod fails with no logsKnown issue class on EKSContact support for the latest chart — newer versions include migration-pod logging
"Error 321: failed to refresh cached credentials" in chatIAM role for Bedrock on the EKS nodes — invalid, expired, or quota-exceededCheck the node role (typically tql-eks-node-role): Bedrock permissions, credential validity, quota (Module 3)
Recurring "invalid model identifier" health errorsBedrock model access / inference profiles (Module 3.3)Bedrock console → Model access; check the globalInference setting against what's provisioned
Sandbox workers in Error seconds after startWorker image issue (e.g., a missing Python dependency in a specific image version)Check worker pod logs for the import traceback; usually resolved by a chart/image upgrade
Auth fails after a secret changeThe Module 5.3 gotcha — pods holding stale secretskubectl rollout restart the affected deployments
Auth fails after IdP changesPartial OIDC config (all four fields together), or role-sync removing rolesVerify the four fields; check preserve_admin_role; check IdP group claims

Worth knowing about restarts: multiple old ReplicaSets on compute-engine are normal after iterative upgrades; a pod much younger than its peers usually means a manual restart happened — check kubectl.kubernetes.io/restartedAt before attributing mystery behavior to anything deeper.

6.2 · TextQL Doctor — diagnostics without giving access

Self-hosting means TextQL support can't see your cluster. TextQL Doctor closes that gap without opening your perimeter:

  1. You run the doctor script in your deployment (TextQL support provides it / it ships with the deployment tooling).
  2. It collects deployment diagnostics — pod states, compute-engine logs, Helm chart version and values, Kubernetes configuration — into a single encrypted file (textql-doctor-<date>-<hour>.encrypted.txt).
  3. You send that file to TextQL support. Only TextQL holds the decryption key — the file is unreadable in transit and to anyone else.
  4. TextQL analyzes it against the exact chart version you're running and known-issue history, and returns findings — typically distinguishing config-on-your-side (an IAM grant, a values key) from fix-on-TextQL's-side (a chart/image issue) in the first pass.

What to do before generating a doctor file, so the cycle is one round instead of three: note your chart version (helm list), capture when the symptom started and what changed around then (upgrade? secret rotation? IdP change? — the catalog above is ordered by exactly these), and include the affected pod names.

6.3 · Escalation that gets same-day answers

The escalation package, assembled:

  1. Chart version + when it was installed/upgraded
  2. The symptom, when it started, and what changed around that time (the most diagnostic single fact — config changes masquerade as version regressions surprisingly often)
  3. Which catalog row (6.1) you suspect and what you already ruled out
  4. The doctor file
Production note for regulated environments: the doctor file contains logs and configuration. The encryption protects it in transit, and TextQL's analysis practice is to redact sensitive values — but if your compliance posture requires it, review what the script collects with your security team once, up front, so generating one during an incident needs no new approval.
