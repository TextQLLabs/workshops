TextQL Admin & Governance Workshop

A hands-on workshop for workspace administrators: identity and SSO, roles and permissions, connector governance, capability and model controls, monitoring, and the day-to-day operations of running TextQL safely at scale.

It runs as short, hands-on modules with exact click-paths, copy-paste prompts, what you'll see, and a checkpoint before moving on. Total time: about 2.5 hours.

What you'll be able to do

MODULE 1

Identity: SSO & SCIM

Login through your IdP; joiners and leavers handled automatically.

MODULE 2

Roles & permissions

Least-privilege custom roles and the sharing model, demystified.

MODULE 3

Connector governance

Who reaches which data, with which credentials, with what guardrails.

MODULE 4

Capabilities & models

Org-wide tool toggles, model allowlists, limits, and spend.

MODULE 5

Monitoring & audit

Audit log, thread-quality observability, and automated weekly review.

MODULE 6

Governance operations

Patch review, access requests, on/offboarding, and the runbook.

Before you start

  1. You need the admin role — ideally in a staging org for Modules 1–2.
  2. Work through modules in order: identity → authorization → data → monitoring → operations.
  3. Steps give exact click-paths (e.g., Settings → Roles) or Prompts to ask Ana. Adapt anything in [brackets].
  4. Don't skip Checkpoints — several settings have org-wide blast radius; checkpoints verify you haven't locked anyone out.
Configuration details follow the current product docs at docs.textql.com. VPC / self-hosted deployments: substitute your own host wherever you see app.textql.com.
For facilitators — running this as a guided session

T-minus-1-day pre-flight: run the workshop's key prompts end-to-end in the session workspace — confirm logins, connectors, and the features this workshop touches are enabled for every attendee; have a fallback demo workspace ready in case a customer connector fails live. Pacing: when a long prompt is running (2–4 min), fire it first, then discuss the concept while Ana works — never watch a spinner in silence. If behind schedule, cut sections marked optional, never the checkpoints. Group sessions: attendees drive, you narrate; collect every miss or wrong answer in a shared doc — that list is the ontology backlog. With 10+ attendees on one warehouse, stagger the heavy prompts.

0.2 · The two other admin surfaces

  • Connectors (sidebar) — data source management, credentials, access. Module 3.
  • Ontology / Context Library (sidebar) — governed business knowledge; admins review patches. Module 6.

0.3 · Take a baseline snapshot

PROMPT 
Give me an admin baseline of this organization: how many members and what roles they hold, which connectors exist and whether they are read-only or read-write, which tools are enabled org-wide, and which AI models are enabled. Format it as a table I can save.
You'll see: A configuration snapshot. Save it — it's your before picture, and writing it down is the first governance habit.

0.4 · The mental model: four layers of control

  1. Identity — who can get in at all (SSO, SCIM) → Module 1
  2. Authorization — what a signed-in user may do (roles, permissions, sharing) → Module 2
  3. Data scope — which data their questions can touch (connectors, credentials) → Module 3
  4. Behavior & observability — what tools/models run, within what limits, and how you watch it → Modules 4–5

A request must pass every layer. When you debug "user X can't do Y," walk the layers in this order.

Module 1

Module 1 · Identity: SSO & SCIM

⏱️ 30 min

Goal: move authentication to your identity provider (OIDC), then automate the user lifecycle (SCIM) so joiners, movers, and leavers are handled by your IdP — not by hand.

Do this module in a staging org first if you have one. Identity changes affect everyone's login.

1.1 · Why SSO first

Until SSO is on, users sign in with magic links or Google — fine for a pilot, not for governance. SSO gives you central credential policy (MFA, session length), instant deprovisioning, and a single audit point. Supported: Okta, Microsoft Entra ID (Azure AD), Ping Identity — anything OIDC-compliant.

1.2 · Configure OIDC

Where to click

Settings → Configuration tab → Authentication section → OIDC Settings

FieldWhere it comes from
Redirect URLSystem-generated, read-only — copy it into your IdP as the callback/redirect URI
Display NameYour choice — the login button users see (e.g., "Acme SSO")
Client IDFrom the OIDC app you create in your IdP
Client SecretSame — from your IdP
Issuer URLIdP base URL (e.g., https://yourcompany.okta.com or https://login.microsoftonline.com/<tenant-id>)

Pick your provider from the Identity Provider dropdown (Okta OIDC / Microsoft OIDC / Ping OIDC). Okta has a dedicated step-by-step in the docs.

Order of operations that avoids lockout:

  1. Create the OIDC app in your IdP first (using the Redirect URL from TextQL).
  2. Fill the TextQL form and save.
  3. Test in an incognito window with a test account — keep your current admin session open in another tab.

1.3 · Verify SSO

Incognito → login page → your Display Name appears → authenticate via IdP → land in the workspace. Then confirm the trail:

Where to click

Settings → Audit Log → filter Category = Authentication

You'll see: "Created OIDC provider" and your test "Logged in" events, with actor, timestamp, IP, and auth method.

1.4 · Automate lifecycle with SCIM

SSO controls how people sign in; SCIM controls who exists. With SCIM 2.0 connected, your IdP creates, updates, and deactivates TextQL users automatically — and can push groups.

Where to click

Settings → Configuration tab → SCIM Provisioning section → Create Token

  1. Name the token after the IdP (e.g., "Okta SCIM") and copy it immediately — it is shown once.
  2. In your IdP, add SCIM provisioning to the TextQL app: SCIM Base URL https://app.textql.com/scim/v2 (own host for VPC), Bearer token auth.
  3. Enable: Create Users, Update User Attributes, Deactivate Users, Push Groups.
  4. Ping only: map given_name ← \${user.name.given} and family_name ← \${user.name.family}, or display names won't populate.

1.5 · Test the joiner / leaver loop

  1. Joiner: assign a test user to the TextQL app in your IdP → they appear in Settings → Members.
  2. Leaver: unassign them → they are deactivated in TextQL.
  3. Confirm both in the Audit Log (Category = SCIM Provisioning).
PROMPT 
From the audit log, list all member provisioning and deprovisioning events in the last 30 days. Flag any member created manually rather than via SCIM.
You'll see: The lifecycle trail — and a flag on anyone bypassing the IdP, which after SCIM should be rare and deliberate.

Troubleshooting

SymptomFix
IdP error after login redirectRedirect URL in the IdP must exactly match the system-generated one
Users provisioned but names blankPing: missing given_name/family_name custom attribute mappings (1.4)
Multiple email domains need accessWhitelist each domain in your OIDC security configuration
Locked yourself outUse the still-open admin session (kept per 1.2) to correct the config

Module 2

Module 2 · Roles & Permissions (RBAC)

⏱️ 30 min

Goal: understand the permission model deeply enough to design least-privilege custom roles — and answer the #1 admin question: "why can/can't user X see Y?"

2.1 · The model in one minute

  • Two system roles: admin (everything) and member (scoped). Each user holds exactly one role. Unlimited custom roles on top.
  • Permissions are grouped by resource (Chat, Connector, Dashboard, Playbook, Dataset, Feed, Context, Member, Billing, API Access Key, MCP...) and follow one pattern:
PermissionMeaning
readView public items + private ones explicitly shared with you
read_privateView all private items, even unshared ones
writeCreate and edit any public item of that type
write_privateCreate/edit private items (Dashboard: edit any dashboard, even restricted)
Where to click

Settings → Roles → Manage Permissions. Assignment: Settings → Members → role dropdown. Changes apply immediately.

Two design implications worth internalizing:

  1. write bundles creating your own with editing any public item. You cannot grant "create dashboards but don't touch others' public dashboards" — keep fewer things public instead.
  2. No record-level control at the role layer. Roles gate resource types, not rows. Row-level security lives in ontology RLS and per-member warehouse credentials (Modules 3 and 6).

2.2 · Read the defaults before changing them

Do: open the member role's permissions and read what a default member actually gets:

ResourceDefault member accessImplication
Chatread, writeCan create public chats, see others' public chats
Connectorwrite (public)Members can create public connectors by default — many orgs tighten this first
Dashboard / Datasetwrite (public)Can create, and edit any public one
FeedwriteCan post and manage agents
ContextnoneCannot edit org context — patches need elevated review
BillingnoneAdmin-only
MemberreadSees the member list, can't manage it
API Access KeyreadCan use public keys, not create them
PROMPT 
Summarize the differences between the admin and member roles in this org as a table: resource, member access, admin access. Highlight anywhere the member role has write access.

2.3 · Design a custom role

The most-requested pattern from real support tickets: a viewer/analyst split and restricting who can publish connectors.

Do: Settings → Roles → Create Role → analyst-restricted → Manage Permissions: Chat read+write; Dashboard read only; Connector read only; Playbook read only; Feed read. Assign a test user, then verify as them: they should fail to create a connector or edit a public dashboard.

Custom roles also scope which connectors, context files, and models the role can access — that's how "Finance sees the finance warehouse, Sales sees the CRM mirror" is done. Connector scoping: Module 3. Model scoping: Module 4.

2.4 · Sharing semantics — the other half of access

  • A private item: visible to owner + explicit shares + read_private holders.
  • A public item: visible to anyone with read — editable by anyone with write.
  • Feed inheritance: a post is visible only if the viewer can read every chat it references. Plain-text posts: anyone with feed read. Admins bypass.
  • Access requests: users hitting a private item can request access; the owner is notified and approves/denies.
PROMPT 
User [email] says they can't see [dashboard/playbook/thread name]. Walk the four layers: do they have a role with read on that resource type, is the item public or private, is it shared with them, and for feed posts — can they read all referenced chats? Tell me the single change that grants access with least privilege.
You'll see: A layer-by-layer diagnosis ending in one least-privilege change. Save this prompt — it answers most access tickets.

2.5 · SCIM groups → roles

If you completed Module 1: push groups from your IdP and map them to TextQL roles. New hire joins the data-analysts IdP group → lands in the right TextQL role on day one, no admin touch.

Troubleshooting

SymptomFix
"Public vs private" confusion from usersRun the 2.4 debugging prompt; it's almost always sharing state, not role
Role changes seem not to applyThey apply immediately — the user needs a fresh thread (selections are fixed per thread)
Two roles aren't enough granularityCustom roles + SCIM group mapping; member baseline = most-restrictive common denominator

Module 3

Module 3 · Connector Governance

⏱️ 25 min

Goal: govern the data layer — which sources exist, who reaches each one, with which credentials, and with what blast radius if something goes wrong. This is where the largest share of real-world admin questions land.

3.1 · Inventory what exists

Where to click

Connectors (sidebar) — note each connector's type, creator, public/private, and read-only vs read-write mode

PROMPT 
List every connector in this org with its type, visibility (public/private), and whether it is read-only or read-write. Flag anything read-write, and anything public that connects to a production database.
You'll see: Your data attack surface in one table. Read-write connectors deserve explicit justification — Ana can run INSERT/UPDATE/DDL through them.

3.2 · The credential decision

ModelHow it worksUse when
Shared service accountOne credential; everyone queries as itSimplicity; non-sensitive or broadly shared data
Per-member OAuth (Snowflake, Databricks)Each member queries as themselves — one-time popup, or silently via SSO token exchangePer-user warehouse audit trails; warehouse-enforced row/column security

Per-member setup (Snowflake sketch): create an OAuth security integration in the warehouse (CREATE SECURITY INTEGRATION ... OAUTH_REDIRECT_URI='https://app.textql.com/auth/snowflake/callback'), retrieve client credentials, select Per-Member OAuth on the connector, paste credentials. SSO token exchange is optional; the popup is the fallback.

Governance principle for shared accounts: the service account's warehouse role is your ceiling — grant the narrowest role that serves the use case, never a superuser. With per-member auth, the warehouse's own grants do the row-level work.

3.3 · Scope connectors by role

The recurring enterprise ask: Finance sees the finance warehouse; Sales sees the CRM mirror; neither sees the other. Custom roles (Module 2) scope which connectors a role can access. Combine with: private connectors, default connector by role, and keeping member Connector permission at read so the catalog stays admin-curated.

Verify as the user, not on paper — as a test user in the restricted role:

PROMPT 
What data sources do I have access to in this chat?
You'll see: Only the scoped connectors. If they see more, check in order: role connector list, connector visibility, second role assignment.

3.4 · Guardrails on what queries can do

  • Read-only mode blocks all DML/DDL regardless of warehouse grants — make it your default posture; read-write is the exception with an owner and a reason.
  • Org limits (Settings → Specs) cap blast radius: 2M SQL rows, 180s query timeout, 360s cell runtime. Raising them is a support request — that friction is a feature.
  • Ontology-layer RLS — fail-closed .tql rules filtering rows by user attributes. The data team authors these; your job is knowing they exist so you don't solve row-level problems with roles.

3.5 · Credential lifecycle

  • Who may create connectors — after 3.3, typically admins or a designated data-platform role only.
  • Rotation — rotate on your security schedule; edit the connector in place; test immediately after.
  • Decommission — deleting a connector orphans dependent assets. First:
PROMPT 
Which dashboards and playbooks depend on the [name] connector? I'm planning to decommission it.
You'll see: The dependency list — migrate or archive these, announce, then delete in a maintenance window.

Troubleshooting

SymptomFix
User can't see a needed connectorLayer-walk: role scope → visibility → was it attached before the thread's first message
Per-member OAuth popup loopsRedirect URI must exactly match the warehouse OAuth integration; check token validity
"Tables in chat don't match the warehouse"The connector credential sees a different schema — compare service-account grants vs the user's own warehouse role
Test passes but queries time outNetwork path (firewall/allowlist) and warehouse queue — see docs Network Configuration

Module 4 · Capabilities, Models & Limits

⏱️ 20 min

Goal: decide what Ana is allowed to do org-wide — tools, AI models, defaults, and resource limits — and scope by role where one size doesn't fit.

4.1 · Tool access control

Where to click

Settings → Capabilities

Org-wide toggles (users can narrow, never widen, in Personal → My Chat Defaults):

ToggleGovernance question it answers
Web SearchMay Ana send queries to the public internet? (data-exfil sensitive orgs often disable)
SQL ExecutionMay Ana run SQL at all?
Ontology Access / EditingMay Ana use the semantic layer; may users propose edits?
File UploadsMay users bring ad-hoc files into chats? (data-ingress policy)
PowerBI / Tableau IntegrationAre BI connectors allowed?
Multiple Connector SelectionCan one chat join across sources? (widens single-thread blast radius)
Environment VariablesMay users set env vars in sandboxes?
Dashboards / History Search / Model Switching / Observability / Methodology DropdownFeature availability

Default Chat Mode (same page) sets pre-selected tools and connectors for every new chat. Set it to your most common safe configuration — defaults are destiny; most users never change them.

4.2 · Model governance

Where to click

Settings → Models — three tabs: Model Catalog, Role Access, Analytics

  1. Model Catalog — enable/disable models (Anthropic Claude, OpenAI GPT, Moonshot Kimi families); set the org default. The catalog is your AI-policy allowlist.
  2. Role Access — per-role model lists. Standard pattern: default roles get the workhorse (Sonnet-class); power roles also get premium (Opus-class, costs more per run); cost-sensitive roles get economy (Haiku/Mini-class).
  3. Analytics — usage by model; check whether allocation matches reality.

Also decide Model Switching (Capabilities): off = everyone uses the role default, simplest cost story; on = users pick per chat from their role's allowed list.

PROMPT 
From model analytics: which models were used most in the last 30 days, by which roles, and what share of total ACU spend does each model represent? Does anything suggest the wrong default for a role?

4.3 · Limits (Specs)

Where to click

Settings → Specs — read-only; changes go through TextQL support

4.4 · Spend awareness

New — Chargeback (Beta)

Administrators can now split the organization's usage bill across internal teams: configurable bill lines, auto-updating rosters, what-if previews, and CSV export — past billing periods stay frozen and reproducible. If internal cost allocation is the blocker to onboarding more teams, this is the feature to turn on.

Usage is metered in ACUs. Three lenses: the TextQL Usage connector (query your own usage in plain English), the Usage API (https://app.textql.com/v1/billing, Bearer token from Settings → Developers → API Keys), and Model Analytics (4.2).

PROMPT 
Show ACU consumption by week for the last 8 weeks, broken down by user. Who are the top 10 consumers, and is any single user trending sharply up?
You'll see: Your spend early-warning system — Module 5 turns it into a scheduled playbook.

Module 5

Module 5 · Monitoring & Auditability

⏱️ 25 min

Goal: know the three monitoring surfaces — audit log (security), observability (quality), usage (spend) — and wire the recurring checks into automation.

5.1 · The audit log

Where to click

Settings → Audit Log — filters: free-text + category + action + date range (Today / 7 / 30 / 90 days)

Every security/admin action: time, actor, action, category, resource; click a row for actor ID, auth method, IP, metadata. Categories include Authentication, Member Management, Roles & Permissions, SCIM Provisioning.

Three drills to build the habit:

  1. Who changed permissions lately? Category = Roles & Permissions, last 30 days. Every event should map to a change you know about.
  2. Failed logins. Category = Authentication, action = Login failed. A burst against one account → check with that user.
  3. Trace one user end-to-end. Search their email: invite → join → roles → logins. Your offboarding-verification and auditor answer.
Audit logs and product metrics can stream to Datadog, Splunk, Grafana, Prometheus, or S3 via OpenTelemetry (docs → Observability Export). If you run a SIEM, wire this — don't make the TextQL UI your only copy.

5.2 · Observability — quality monitoring

New — the People view

Observability now includes a People view: active-people trends, an engagement spectrum, and access-method breakdowns, with custom date-range filtering — your adoption dashboard, next to the quality signals below.

Where to click

Observability (left sidebar, admin-only)

Completed threads are analyzed for quality signals — context gaps, execution errors, user frustration, potential inaccuracies — surfaced as warnings. The Overview tab: run volume by source (threads / playbooks / Slack / feed agents), warning trend, Warning Breakdown ranking, searchable run table; 7–90 day ranges.

The weekly triage loop (15 min): stats bar (warn rate trending up?) → Warning Breakdown → click the top type, read 3–5 threads → classify root cause:

Root causeOwner / fix
Missing context ("Ana didn't know our fiscal calendar")Ontology/context patch — Module 6
Connector errors (timeouts, permissions)Connector config — Module 3
Limit hitsCoach narrower queries, or a limit request — Module 4
Unanswerable questionsEnablement — the self-service workshop

This loop is the operational payoff of governance: warnings → root cause → targeted fix → warn rate down. The Warning Breakdown is your ontology backlog, prioritized by frequency.

5.3 · Spend monitoring

Weekly review: total ACUs vs plan, top consumers, per-model split, anomalies (one user 10x-ing, a runaway playbook). Lenses from Module 4.4.

5.4 · Automate the routine

PROMPT 
Create a playbook called "Admin Weekly Review" that runs every Monday at 8am: (1) ACU consumption last week vs the week before, top 10 users; (2) audit log summary — new members, role/permission changes, failed logins; (3) observability summary — run volume, warn rate vs prior week, top 3 warning types. Flag anything anomalous at the top. Email it to me.
You'll see: The playbook under Playbooks in the sidebar. Confirm schedule + delivery, then let Monday come to you. Optionally add a feed agent for continuous anomaly watching.

Module 6

Module 6 · Governance Operations

⏱️ 20 min

Goal: the recurring human workflows — context/ontology patch review, access requests, on/offboarding — and the runbook that makes it survivable by your successor.

6.1 · Reviewing context & ontology patches

When members teach the platform ("our definition of active user is..."), it lands as a patch — a PR-style proposed change to org context. Members propose; you (or designated owners) approve. Every change is versioned and revertible.

Where to click

Settings → Notifications → Ontology → enable Patch submitted (route to Slack if connected). Also watch Sync failures — a failed git sync means Ana reads stale context; treat as an incident.

Review bar — for each patch ask:

  1. Correct? Does it match how the business measures it? When unsure, ask the metric's business owner — don't judge alone.
  2. Conflicting? Contradicts an existing governed definition? Reconcile — one definition wins, the alternative gets a clearly-named variant — never silently override.
  3. Scoped? Org-wide truth → org context; one team's shorthand → role-scoped context; one person's preference → personal context (no review needed).

6.2 · Access requests

  • Make sure owners handle their own queues (Notifications → Sharing) — you are the escalation path, not the bottleneck.
  • Orphaned items (owner left): you hold read_private/write_private — reassign deliberately, and log it.
  • Periodically check for stuck queues — use the prompt below.
PROMPT 
List private items with access requests pending for more than a week, with each item's owner — those are stuck queues I should nudge.

6.3 · Onboarding & offboarding, end to end

Onboarding (mostly automatic): IdP group → SCIM provisions → group mapping sets role → role scopes connectors, models, defaults. Manual steps: verify the role, send the self-service workshop.

Offboarding (verify, don't assume):

  1. IdP unassignment → SCIM deactivates (verify in Members).
  2. Audit log: confirm the deactivation event.
  3. Reassign owned assets — dashboards, playbooks (scheduled ones keep running!), connectors, pending patches.
  4. Rotate any shared credentials they could access.
PROMPT 
[Departed user email] has left. List everything they own: dashboards, playbooks (note which are actively scheduled), connectors, datasets, and any pending ontology patches. Propose a reassignment plan.
You'll see: A complete asset inventory with a reassignment plan — run this for every departure, real or simulated.

6.4 · Write the runbook

Governance in one admin's head is a bus-factor of one. Use the Admin Runbook template on this workshop's Reference page: decision log, credential inventory and rotation schedule, patch review owners, on/offboarding checklists, escalation paths, and the weekly/monthly cadence. Fill it in now while Modules 1–5 are fresh.
