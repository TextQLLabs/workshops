TextQL Connect Your Data Workshop

A hands-on workshop for data engineers, platform admins, and technical leads: get every kind of data source connected to TextQL correctly the first time — warehouses, private-network databases, BI tools, files, Google Drive, and external APIs — with credentials done right and a validation habit that catches problems before your users do.

Hands-on format: short modules, exact setup steps, copy-paste commands, checkpoints. ~2.5 hours end to end — but most teams run only the modules for sources they actually use.

What you'll be able to do

MODULE 1

Network & credentials

Clear the firewall path; know every credential pattern.

MODULE 2

Warehouse connectors

Snowflake, BigQuery, Redshift, Databricks, PostgreSQL — production-grade.

MODULE 3

Private networks

SSH tunnels through a bastion for databases with no public endpoint.

MODULE 4

BI tools

Tableau and Power BI — including the sync step everyone misses.

MODULE 5

Files, Drive & APIs

Zero-setup files, service-account Sheets, secure API access.

MODULE 6

Validate & operate

The five-question smoke test, rotation, resync, decommission.

How to use this workshop

  1. You need the connector:write permission (members have it by default unless your admin tightened it).
  2. Do Modules 0–1 always — they prevent the failure modes behind most connector tickets.
  3. Jump to the module for your source type; each warehouse section is self-contained.
  4. Finish with Module 6 regardless of path — the smoke test is the difference between "test passed" and "actually works."
Setup steps follow current product docs at docs.textql.com. SaaS deployment assumed; VPC / on-prem deployments skip IP whitelisting and confirm network requirements with their TextQL representative.
For facilitators — running this as a guided session

T-minus-1-day pre-flight: run the workshop's key prompts end-to-end in the session workspace — confirm logins, connectors, and the features this workshop touches are enabled for every attendee; have a fallback demo workspace ready in case a customer connector fails live. Pacing: when a long prompt is running (2–4 min), fire it first, then discuss the concept while Ana works — never watch a spinner in silence. If behind schedule, cut sections marked optional, never the checkpoints. Group sessions: attendees drive, you narrate; collect every miss or wrong answer in a shared doc — that list is the ontology backlog. With 10+ attendees on one warehouse, stagger the heavy prompts.

Module 0

Module 0 · Before You Connect

⏱️ 15 min

Goal: make the three decisions that determine everything downstream — source type, credential model, and scope — before touching any form.

0.1 · Know your options

PathBest forSetup cost
File upload (CSV/Excel in a thread)Instant analysis, POCs, one-off dataZero — drag and drop
Warehouse / database connectorProduction use, live data, recurring questionsMinutes to an hour (this workshop)
BI tool connector (Tableau, Power BI)Analyzing existing dashboards alongside warehouse dataModerate (Module 4)
Starting a POC? Upload a file today, connect the warehouse when ready for production. Don't block a pilot on firewall tickets.

Supported: Snowflake, BigQuery, Redshift, Aurora (MySQL & PostgreSQL), Azure Synapse, PostgreSQL, Supabase, MySQL, ClickHouse, Athena, Databricks. BI: Tableau, Power BI. Plus Google Drive and external APIs (Module 5).

0.2 · The Connectors page

Where to click

Connectors (left sidebar) — add connectors, preview synced tables, resync after schema drift, manage API accesses (API tab)

Actions are gated by connector:write — without it, create/edit/delete/manage-access are hidden. Viewing and using connectors needs no write permission.

0.3 · Decision 1 — service account, not personal credentials

  • A Snowflake service user with key-pair auth — not your own login
  • A GCP service account with exactly two BigQuery roles — not an owner key
  • A Databricks PAT from a service principal where possible — not your personal token

Personal credentials break when you leave or rotate a password, can't be least-privileged without affecting you, and muddy warehouse-side audit.

0.4 · Decision 2 — scope: what should Ana see?

  • Database/schema scoping — point at the analytics DB or mart schema, not the whole instance. Less noise = better SQL, faster sync, smaller blast radius.
  • Read-only vs read-write — read-only is the right default; read-write needs an owner and a reason.
  • Grant-level scoping — SELECT on what's needed, nothing more.

0.5 · Decision 3 — who in TextQL gets this connector?

Public vs private is one dropdown at creation but a migration after users build on it. Production warehouses with sensitive data usually start private and get role-scoped.

PROMPT 
List the connectors that already exist in this org with their types and visibility. I'm about to add [source] — flag anything that looks like a duplicate or overlapping source.
You'll see: The current fleet — surprisingly often the source is already half-connected, and your job is consolidation, not creation.

Module 1

Module 1 · Networking & Credentials 101

⏱️ 20 min

Goal: clear the network path and understand the credential patterns — the two causes of almost every "connection failed" ticket.

1.1 · The IP allowlist

For SaaS deployments, TextQL connects from two fixed IPs. Whitelist both:

44.229.62.69
54.69.138.147
VPC, on-prem, single-tenant: this does not apply to you — confirm network requirements with your TextQL representative. BigQuery also needs no IP whitelisting (OAuth/service account over Google's API).

1.2 · Provider-specific firewall steps

AWS (RDS, Aurora, Redshift): RDS Console → database → Connectivity & Security → VPC security group → Inbound rules → Edit. Two rules per engine port, one per IP (/32):

EngineTypePort
MySQL / Aurora MySQLMYSQL/Aurora3306
PostgreSQL / Aurora PostgreSQLPostgreSQL5432
RedshiftRedshift5439

Azure: resource → Networking → Firewalls → two rules, Start IP = End IP = each TextQL IP. Google Cloud SQL: instance → Connections → Authorized networks → two /32 entries. Databricks: add both IPs to workspace IP access lists if used.

1.3 · Verify the path before you blame the credential

A timeout is almost always network (firewall, wrong host/port, private subnet); an authentication error is the credential. Fix in that order. No public endpoint at all → Module 3.

1.4 · The credential patterns you'll meet

PatternUsed byYou provide

Handling rules: dedicated service identity; copy in your secrets manager before pasting (forms redact after save); record the rotation date — credential expiry is the #1 "worked for months, just stopped" cause.

Module 2

Module 2 · Warehouse Connectors

⏱️ 40 min

Goal: connect each major warehouse with production-grade auth. Every section: prepare the service identity → fill the form → test. Do the sections you use (~10 min each). All start: Connectors → New Connector → pick the source.

2.1 · Snowflake

Auth: key-pair only for new connectors (Snowflake deprecates single-factor passwords for service users by Oct 2026; TextQL connects as a service user).

PROMPT 
Generate a 2048-bit RSA key pair for Snowflake key-pair auth in your sandbox: an unencrypted PKCS#8 private key and its public key. Give me the private key to store in my secrets manager, and the public key with the header/footer lines stripped, ready for ALTER USER.
You'll see: Both keys. Vault the private key immediately — it goes into the connector form, never into a shared doc.
Prefer the terminal?

Generate the pair locally instead:

# Private key
openssl genrsa 2048 | openssl pkcs8 -topk8 -inform PEM -out rsa_key.p8 -nocrypt
# Public key
openssl rsa -in rsa_key.p8 -pubout -out rsa_key.pub
ALTER USER textql_svc SET RSA_PUBLIC_KEY='<public key, no header/footer lines>';
FieldExample
Account Identifierxy12345.us-east-1
Database / Schema / WarehouseANALYTICS_DB / PUBLIC / COMPUTE_WH
Role (optional)TEXTQL_ROLE
Username + Private Keyservice user + entire rsa_key.p8 including header/footer
The Role field is your governance lever: create a TEXTQL_ROLE with explicit SELECT grants rather than reusing a broad human role. Upgrade path: per-member OAuth (Admin workshop, Module 3).

2.2 · BigQuery

Prepare: GCP Console → IAM → Service Accounts: create textql-connector@... with exactly BigQuery Data Viewer + BigQuery Job User; download a JSON key.

Form: Project ID · Dataset ID (optional but recommended — scopes introspection and the test) · Service Account Key (full JSON) · Region Qualifier.

Test behavior: with a Dataset ID the test verifies that dataset; without one it checks the account can list datasets in the project — a key that reads one dataset but can't list will "fail" unscoped while being perfectly usable scoped. Scope it.

2.3 · Redshift

Password path: Host (cluster endpoint), Port 5439, User, Password, Database, Schema, Dialect (Redshift native vs Postgres-compatible).

IAM role path: Role ARN · AWS Region · Cluster ID · Access Key ID/Secret (both or neither — omit both and TextQL's own IAM credentials assume the role) · Database User (provisioned clusters with Group Federation disabled).

2.4 · Databricks

Prepare: SQL Warehouses → create/reuse → start it → Connection details → copy Server hostname and HTTP path. Generate a PAT (User Settings → Access tokens) — prefer a service principal's token; set a tracked expiration.

Form: Host (without https://) · Port 443 · HTTP Path · Catalog · Schema · PAT.

The classic gotcha: a stopped SQL warehouse. The test may pass after a slow warm-up, then morning queries crawl. Set auto-stop sensibly; warn users about first-query warm-up.

2.5 · PostgreSQL (and the password family)

Host, Port 5432, Username, Password, Database, Schema — readable from postgresql://user:pass@host:5432/db. Same pattern: MySQL, Aurora, Supabase. Create a read-only user first:

CREATE USER textql_reader WITH PASSWORD '...';
GRANT CONNECT ON DATABASE mydb TO textql_reader;
GRANT USAGE ON SCHEMA analytics TO textql_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO textql_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA analytics
  GRANT SELECT ON TABLES TO textql_reader;

The ALTER DEFAULT PRIVILEGES line keeps future tables visible — its absence is why "new tables don't show up" tickets happen. Private subnet → Module 3.

2.6 · After any connector: the first sync

PROMPT 
Pull the information schema for this connector. List the tables you can see with row counts where cheap to get, and flag any schemas you expected but can't access.
You'll see: What Ana actually sees — the credential's view, not yours. "Tables don't match the warehouse" is grants, not bugs: compare the service identity's grants to your own.

Module 3

Module 3 · Private Networks & SSH Tunnels

⏱️ 15 min

Goal: connect a database with no public endpoint — through a bastion host (SSH tunnel). Currently supported for PostgreSQL connectors; other engines → VPC deployment conversation.

3.1 · When a tunnel is the right answer

  • Database in a private VPC with no public endpoint
  • Policy requires all external access through a bastion
  • You can't or won't whitelist external IPs on the database itself
TextQL  ──SSH──▶  Bastion Host  ──TCP──▶  PostgreSQL (private subnet)

The allowlist moves: TextQL's IPs go on the bastion's security group (inbound SSH), not the database's.

3.2 · Prepare the bastion

  1. Bastion reachable on its SSH port, inbound SSH allowed from 44.229.62.69 and 54.69.138.147
  2. A dedicated OS user (e.g., textql-tunnel) — not a shared admin
  3. SSH key pair: public key authorized on that user; keep the PEM private key
  4. Bastion → database route open on the DB port
  5. Recommended: the bastion's host public key — /etc/ssh/ssh_host_ed25519_key.pub

3.3 · Fill the form

In the PostgreSQL connector form, check Connect via SSH tunnel (bastion host):

FieldValue
SSH Host / PortBastion address; default 22
SSH Usernametextql-tunnel
SSH Private KeyPEM (starts -----BEGIN)
SSH Host Public KeyOptional, recommended — verifies bastion identity (MITM protection)
In the main connection fields: Host URL and Port are the database's private address — the one reachable from the bastion. Putting a public-looking endpoint there is the most common mistake.

The SSH key is stored encrypted, never shown after save; rotate by editing the connector.

3.4 · Diagnose failures in order

ErrorBroken hopCheck
"Failed to establish SSH tunnel"TextQL → bastionBastion reachable; username/key correct; PEM format; TextQL IPs allowed inbound
"Connection test failed" (tunnel OK)Bastion → DBPrivate host/port correct; bastion has network access; DB SG allows bastion
"Host key verification failed"Identity checkHost public key doesn't match — re-fetch from the bastion

Module 4

Module 4 · BI Tools: Tableau & Power BI

⏱️ 25 min

Goal: connect the BI layer so Ana reads your existing dashboards — and never skip the post-creation sync/collection step, the top BI-connector support theme.

Both BI integrations also have an org-level Capabilities toggle (Admin & Governance workshop, Module 4). Connector type missing? Look there first.

4.2 · Tableau

Prepare: generate a Personal Access Token; note PAT name (ID) and value. Decompose your URL — from https://10ax.online.tableau.com/#/site/textqldev/home: Server = https://10ax.online.tableau.com, Site = textqldev (after site/).

Form: Connector Name · Server URL · Site · PAT ID · PAT Value → Create.

The step people miss: creating the connector connects the server; Ana sees nothing until you build a collection.
Where to click

Connectors → your Tableau connector → New collection → project → workbook → select views (and linkable published datasources)

Scope deliberately — expose certified, maintained workbooks, not all 400 on the server. Default limit: 10,000 rows per Tableau query.

PROMPT 
What dashboards and views do you have access to from this Tableau connector? Summarize what each one shows.
You'll see: Exactly the views in your collection — and only those.

4.3 · Power BI

The most setup-intensive connector: Azure AD app registration (service principal). Needs Azure portal access, Power BI workspace admin, Pro/Premium license.

Step 1 — App registration: portal.azure.com → Azure AD → App registrations → New registration (this directory only; no redirect URI) → record Application (client) ID and Tenant ID → Certificates & secrets → New client secret → record the value immediately (shown once) and calendar its expiry.

Step 2 — Power BI side: tenant setting allowing service principals to use Power BI APIs (once, by the Power BI admin, usually via a security group); add the app as Member/Viewer on each workspace Ana should read.

Step 3 — TextQL form: Client ID · Client Secret · Tenant ID → Create.

Step 4 — Sync: select workspaces/datasets to expose, then verify in a chat:

PROMPT 
What Power BI workspaces and datasets can you see through this connector? Summarize what each one covers.
You'll see: Exactly the workspaces the service principal was added to — and only those.
SymptomCause
Auth succeeds, no workspaces visibleService principal not added to workspaces, or tenant API setting off
Worked, then stopped after monthsClient secret expired (max 24 mo) — rotate in Azure, update connector

Module 5

Module 5 · Files, Google Drive & APIs

⏱️ 20 min

Goal: the three non-warehouse intake paths — ad-hoc files, Drive/Sheets via service account, and external APIs through the secure proxy.

5.1 · File uploads — zero setup

Attach a CSV/Excel in a thread (the "+" button) and ask away. Right for: POCs, one-offs, data not in any warehouse. Know: 1M rows / 100 cols default; can be disabled org-wide (Capabilities); a file lives with its thread — not a governed source. A recurring file is your signal to connect the system it came from.

PROMPT 
Profile this file: columns, types, null rates, and anything that looks like a data quality problem. Then suggest three questions worth asking it.

5.2 · Google Drive & Sheets — the service account pattern

Part 1 — GCP Console: create/reuse a project → enable Google Drive API and Google Sheets API → create a service account → download a JSON key.

Part 2 — the step everyone forgets: a service account sees nothing by default. Share each file or folder with the service account's email exactly like sharing with a person. Folder-level sharing covers contents.

Part 3 — store the credential:

Option A — API Access (preferred)Option B — Env var
HowConnectors → API tab → + New API Access → Google Cloud template → paste JSONJSON as an env var referenced in Python
SecurityAna never sees the raw key — proxy does JWT exchange, injects short-lived tokensKey material in the sandbox env
PROMPT 
Open the Google Sheet "[name]" and read me the first 10 rows of the first tab.
You'll see: The sheet contents — or a failure that is, 90% of the time, Part 2: the sheet isn't shared with the service account email.

5.3 · External API connectors

Where to click

Connectors → API tab → + New API Access

  • Templates for common providers — paste token, Test Connection.
  • Custom — whitelist the domain, attach token/OAuth auth (or none for public APIs); Advanced Options for the unusual.
  • GCP-style — service-account JSON; proxy does the JWT exchange; sandbox sees only a placeholder env var.

Governance: the API tab can be disabled org-wide (missing = admin decision, not a bug). A user reaches a domain when they can access at least one connector for it — domain whitelisting is the perimeter; document who approves additions. Rate limits are the API's: for high-volume sources (CRMs), prefer a warehouse mirror for reads, keep the API for writes.

PROMPT 
Using the [name] API access, make a simple authenticated request (e.g., fetch my account info or list one page of records) and show me the response status.

Module 6

Module 6 · Validate & Operate

⏱️ 20 min

Goal: the difference between "the test passed" and "production-ready" — a repeatable smoke test, plus rotation, resync, monitoring, and decommission habits.

6.1 · The five-question smoke test

Run in a fresh chat against every new connector before announcing it:

1 · Visibility

PROMPT 
List the schemas and tables you can see through this connector. Anything you'd expect for [domain] that's missing?

2 · Read

PROMPT 
Run a trivial query: count rows in [small table] and show 5 sample rows.

3 · Breadth

PROMPT 
Query [table in a different schema you intend to expose]. Does access work across all intended schemas?

4 · Write protection (read-only connectors)

PROMPT 
Attempt to create a temp table. I expect this to FAIL — confirm the connector is read-only.

5 · Scale behavior

PROMPT 
Run a realistic analytical query for this source: [a join + aggregation typical of real use]. How long did it take?
You'll see: Pass/fail on each. #1 catches grant gaps, #4 catches accidentally read-write connectors, #5 catches the stopped-warehouse / timeout class before a user does.

6.2 · Schema drift and resync

Warehouses evolve; the schema snapshot doesn't follow automatically. Connectors → connector → Resync after tables are added/renamed/dropped. Habit: wire resync into your dbt/ETL release checklist. "Ana doesn't see the new table" → resync is triage step 1 (and check the Postgres default-privileges grant, Module 2.5).

6.3 · Credential rotation

CredentialRotation reality
Snowflake key-pairNew pair → ALTER USER ... SET RSA_PUBLIC_KEY → update connector
Databricks / Tableau PATThey expire. Calendar at creation; regenerate + edit connector
Power BI client secretExpires (max 24 mo) — the #1 "worked then stopped" cause
GCP JSON keysNew key on same service account → update → delete old key
DB passwordsPer your security schedule
Always rerun the smoke test immediately after rotation — a typo'd key otherwise fails at a user's next query.

6.4 · Monitor the fleet

  • Observability (admin sidebar) — connector errors surface as thread warnings; weekly triage catches degradation early.
  • Stale data symptoms — usually upstream ETL; connector-level causes: stale replica, deprecated table. Document refresh cadence on the connector description.
  • Quarterly review — still used? rotation current? scope right? owner present?
PROMPT 
For each connector in this org, when was it last successfully used in a thread? Flag any unused for 60+ days as decommission candidates.

6.5 · Decommission without breakage

  1. Ask Ana what depends on it — prompt below.
  2. Migrate or archive dependents; announce.
  3. Delete in a maintenance window; revoke the credential at the source too (warehouse user / PAT / app registration).
  4. Confirm in the audit log.
PROMPT 
Which dashboards, playbooks, and recent threads depend on the [name] connector? I'm planning to decommission it.
