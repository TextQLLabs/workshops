Embed TextQL in Your Product

A workshop of short, hands-on modules for developers and product teams putting Ana-powered analytics inside their own application — from a one-line iframe to a fully custom chat UI driven by the API, with the auth, multi-tenancy, and production hardening done right.

Total time: about 2.5 hours.

Builds directly on the Developer Workshop (API & MCP) — API fundamentals (keys, the v2 REST surface, streaming basics, the sandbox) live there and aren't re-taught; this workshop is about putting those pieces inside your product.

Who this is for

  • Engineers embedding analytics in an internal portal or a customer-facing SaaS — you should have completed (or skimmed) the Developer Workshop first
  • Product teams scoping "AI analyst" features without building the analyst
  • Platform teams who'll own the auth, tenancy, and cost model underneath

How to use this workshop

  1. Prerequisites: completed (or skimmed) the Developer Workshop; admin access for service-account creation; a connected data source to embed against.
  2. Work in order — Module 1's auth design is load-bearing for everything after it.
  3. Code samples are curl and Python; the embedding surface details follow the current guide at docs.textql.com/core/guides/embedding-ana and the API reference — verify against them when building, as the surface evolves.
  4. Where a capability is deployment-dependent, the module says so for that item specifically.
For facilitators — running this as a guided session

T-minus-1-day pre-flight: run the workshop's key prompts end-to-end in the session workspace — confirm logins, connectors, and the features this workshop touches are enabled for every attendee; have a fallback demo workspace ready in case a customer connector fails live. Pacing: when a long prompt is running (2–4 min), fire it first, then discuss the concept while Ana works — never watch a spinner in silence. If behind schedule, cut sections marked optional, never the checkpoints. Group sessions: attendees drive, you narrate; collect every miss or wrong answer in a shared doc — that list is the ontology backlog. With 10+ attendees on one warehouse, stagger the heavy prompts.

Module 0 · The Embedding Decision Map

⏱️ 15 minutes

Goal: know the four embedding surfaces, what each costs to build, and which fits your product need.

0.1 · The four surfaces

SurfaceWhat it isBuild effortYou get / you give up
Share linksSend users to TextQL-hosted threads/dashboardsNoneZero build; zero UI control — users leave your app
Embedded UI (iframe)The full Ana chat (or a dashboard) inside your page: https://app.textql.com/embed?authKey=...HoursReal product surface with tool/connector lockdown via URL params; TextQL's UI, not yours
Chat via APIYour own UI; conversations driven through the Chat API (streaming or one-shot)Days–weeksTotal UI control, your design system; you own the conversation UX
MCP integrationAna as a tool inside AI clients (covered in the Developer Workshop, Module 4)MinutesGreat for internal/IDE surfaces; not a product embed

0.2 · Match surface to product need

Product needSurface
Internal portal: "give the ops team Ana on the intranet page"Iframe — fastest credible embed
Customer-facing SaaS: analytics inside your product, your brandChat via API (Module 2) — or iframe to validate demand first

0.3 · The escalation path is a feature

These aren't either/or: the standard adoption arc is share links → iframe → API, with each step validating demand before the next step's build cost. The auth work in Module 1 carries across all of them — which is why it comes first.

Do: write one sentence: "We are embedding [surface] to serve [user] inside [product location], and success looks like [metric]." Everything after this module is implementation of that sentence.

Module 1

Module 1 · Auth & Scoped Access

⏱️ 20 minutes

Goal: the non-negotiable security module — service accounts, scoped short-lived keys, role-based data access, and the rule that makes everything else safe: never ship an org-admin key in a client.

1.1 · Two identity types

Personal API KeyService Account Key
Acts asYouA dedicated bot identity
RolesYour roles (change over time)Fixed at creation (immutable)
Survives employee turnoverNoYes
Best forDev, testing, scriptsProduction embeds, automations

Click-path: Settings → Developers → API Keys (personal) / Service Accounts tab (create with name, description, immutable roles, owner — then generate keys from the service account's detail page).

The production rule: embeds run on service-account keys, never personal ones. A personal key dies with its owner's departure or role change; your embed shouldn't.

1.2 · Roles scope everything

The embedded experience shows exactly what the key's identity can access — connectors, and context scoped at three levels:

ScopeWho sees it
OrganizationEveryone in the org
RoleOnly identities holding that role
ConnectorOnly when querying that data source

So the design move is: create a role per embed audience (e.g., embed-support-portal), grant it only the connectors and ontology folders that audience should reach, and create the service account with exactly that role. The embed can then never leak beyond it — not by good behavior, by construction. (Role mechanics: Admin & Governance, Module 2.)

1.3 · Mint short-lived scoped keys per session

For production, don't bake one long-lived key into anything. Your backend mints scoped, expiring keys on demand via the CreateApiKey RPC:

# list available roles (to get role UUIDs)
curl 'https://app.textql.com/rpc/public/textql.rpc.public.rbac.RBACService/ListRoles' \
  -H 'Content-Type: application/json' \
  -H 'connect-protocol-version: 1' \
  -H 'Authorization: Bearer YOUR_MASTER_API_KEY' \
  --data-raw '{}'

# mint a 1-hour key scoped to a role
curl 'https://app.textql.com/rpc/public/textql.rpc.public.rbac.RBACService/CreateApiKey' \
  -H 'Content-Type: application/json' \
  -H 'connect-protocol-version: 1' \
  -H 'Authorization: Bearer YOUR_MASTER_API_KEY' \
  --data-raw '{"expirySeconds": 3600, "assumedRoles": ["ROLE_UUID"]}'

The response returns apiKey (for Bearer auth against the API) and apiKeyHash (for embed URLs via ?authKey=HASH). The per-session pattern:

def get_embed_url_for_user(user):
    role_map = {"support": [SUPPORT_ROLE_UUID], "finance": [FINANCE_ROLE_UUID]}
    resp = requests.post(
        "https://app.textql.com/rpc/public/textql.rpc.public.rbac.RBACService/CreateApiKey",
        headers={"Content-Type": "application/json",
                 "connect-protocol-version": "1",
                 "Authorization": f"Bearer {MASTER_KEY}"},
        json={"expirySeconds": 3600, "assumedRoles": role_map[user.role]},
    )
    return f"https://app.textql.com/embed?authKey={resp.json()['apiKeyHash']}"

1.4 · The three rules

  1. Never ship a long-lived key in client code. The master key lives server-side only; clients receive minted, expiring, role-scoped keys (or the URLs containing their hashes).
  2. Least privilege by construction: one role per embed audience; the service account holds only it; the minted keys assume only it.
  3. Revocation is an admin surface: admins see and can revoke all keys org-wide under Settings → Developers → API Keys — know that path before the incident, not during.

If your org runs SSO, role assignment can also flow from IdP groups (mapped at login), which keeps the role_map in 1.3 aligned with your identity provider rather than hand-maintained.

SymptomFix
Embed shows data the user shouldn't seeThe key's role is over-scoped — check the role's connector and context grants, not the embed code
Embed broke when an engineer leftIt ran on their personal key — move to a service account (1.1)
Keys work in dev, 401 in prodExpiry: minted keys are short-lived by design; mint per session, don't cache across them

Module 2

Module 2 · Embed Chat in Your App

⏱️ 25 minutes

Goal: drive a full conversation through the Chat API with streaming into your own UI — thread lifecycle, follow-ups, and clarifying questions handled programmatically.

API fundamentals (bases, sync vs stream, retrieval) are the Developer Workshop, Modules 0–1. This module is the product-integration layer on top. Note the API surface has two generations — the v2 REST API (/v2/..., SSE streaming) and the v1 surface the embedding guide documents (/v1/chat, /v1/stream via Connect-RPC, with official SDKs). Verify which your deployment exposes and prefer v2 + SDK where available; the patterns below are generation-agnostic.

2.1 · The conversation loop

Your app's chat feature is a loop around three operations:

  1. Start or continue — send a question; omit chatId to start, pass it to continue the same conversation (server-side state — you never re-send history)
  2. Stream the work — render Ana's progress as it happens
  3. Fetch the artifacts — pull the completed chat with its assets (Module 3)

One-shot (backend jobs, no partial display) vs streaming (anything user-facing):

from textql import TextQLClient

client = TextQLClient(api_key=minted_key)   # Module 1's short-lived key

tools = {
    "connector_ids": [TENANT_CONNECTOR_ID],
    "sql_enabled": True,
    "python_enabled": True,
    "ontology_enabled": True,
    "web_search_enabled": False,            # lock down what the embed can do
}

# streaming — the user-facing path
for event in client.chat.stream(question=user_question, tools=tools):
    if event.HasField("text"):
        ui.append_token(event.text)          # live typing into your component

Two product-relevant details in that snippet: the tools block is your capability lockdown (an embed that shouldn't web-search has it off at the request level, not the UI level), and tool configuration is locked for the duration of a chat — changing tools means starting a new chat, so design your UI's "new conversation" affordance accordingly.

2.2 · Render the stream like a product, not a terminal

The stream carries more than text tokens: metadata, tool steps, preview URLs, and a final completion status. The UX mapping that works:

Stream signalYour UI
Metadata / chat startedShow the thread as created; persist the chatId immediately
Tool steps (SQL running, Python running)Status line ("Querying your data…") — not the raw step dump
Text tokensLive-append into the answer bubble
Preview/asset URLsRender placeholders; hydrate via Module 3's fetch
Completion statusEnable the input box again; persist final state

Persist the chatId at start, not at completion — if the user navigates away mid-stream, you can recover the thread.

2.3 · Handle the clarifying question

Ana sometimes responds to ambiguity with a question back ("Which revenue — recognized or bookings?"). In an embedded product this is a feature — if your UI treats it as a normal assistant turn:

  • Render it as a message; the user's reply continues the same chatId — the loop already handles it.
  • For embeds where round-trips are expensive (support-bot surfaces), pre-empt ambiguity instead: enrich the question server-side with context you already know ("For tenant [X], using the governed revenue definition: …") so the clarifying turn rarely triggers.
  • Never silently re-ask with a guessed disambiguation — you'd be reintroducing the exact failure mode the clarifying question exists to prevent.

2.4 · Thread lifecycle in your product

Decide and implement three policies now:

PolicyThe questionCommon answer
PersistenceDo users see past conversations?Store chatIds keyed to your user; list + resume via the API
ContinuationOne long thread or fresh-per-question?Fresh per topic; continue within a topic (tool lock pushes this way too)
Escape hatchCan users open the full thread in TextQL?For internal embeds, yes — link out; for customer-facing, usually no

Module 3

Module 3 · Embed Answers & Visuals

⏱️ 20 minutes

Goal: fetch results, charts, and reports for rendering in your product's own components — plus the standalone interactive HTML option for answers that travel.

3.1 · The artifact model

A completed chat carries assets — charts, files, tables, dashboards Ana produced — retrievable by fetching the chat (GET /v2/chats/{id} on the v2 surface; the chat-get call on v1). Your rendering pipeline:

chat = client.chat.get(chat_id)          # or GET /v2/chats/{id}

answer_text = chat.final_message         # the prose answer
for asset in chat.assets:
    if asset.type == "chart":
        ui.render_image_or_embed(asset.url)
    elif asset.type == "table":
        ui.render_table(fetch(asset.url))   # render in YOUR table component
    elif asset.type == "file":
        ui.offer_download(asset.url)

During streaming (Module 2), preview URLs arrive as events — render placeholders live, then hydrate from the completed chat for the persistent view.

3.2 · Numbers as product data, not prose

For product features that need the number (a KPI card, a badge) rather than a conversation, shape the request so the answer is machine-consumable — the specification-grade prompting from the Developer Workshop, Module 1.4, applied to embeds:

PROMPT 
Total [metric] for the last complete month vs the prior month. Answer as JSON: {"value": n, "prior": n, "change_pct": n} and nothing else.

Parse defensively (it's a model, not an RPC — validate the shape, fall back to displaying prose if parsing fails), and cache aggressively: a KPI card asked identically by every visitor is the canonical caching case (Module 6).

3.3 · Reports and the standalone HTML option

For report-shaped outputs, two embedding-friendly forms:

  • PDF — ask for the report as a PDF; the asset URL feeds your existing document viewer/download flow.
  • Standalone interactive HTML — ask for a self-contained HTML report with embedded data and working filters. This is the underrated embed surface: it renders in a sandboxed iframe in your product with no live connection at all — no auth, no API calls from the client, data frozen at generation time. For "monthly report inside the customer portal," it's often the right risk profile precisely because it can't query anything.
PROMPT 
Build this analysis as a standalone interactive HTML report: [metrics] by [dimension] with a dropdown filter for [segment]. All data embedded in the file, working offline. Keep it under [2] MB.
You'll see: an HTML asset your product serves from its own storage — the embed that can't leak, because it can't fetch.

3.4 · Asset URLs and your perimeter

Treat asset URLs operationally: fetch them server-side and re-serve through your product's storage/CDN rather than hot-linking from client code. Three reasons: your auth perimeter stays intact (the client never holds TextQL credentials — Module 1's rule), you control retention (the artifact lives as long as your product needs it), and email/external surfaces that can't authenticate still render (auth-protected hot-linked images breaking in emails is a classic failure).

Module 4

Module 4 · Embedded UI & Dashboards

⏱️ 20 minutes

Goal: the iframe surfaces — full Ana chat embedded with tools and connectors locked down per embed, dashboards inside other tools, and refresh behavior understood.

4.1 · The embed URL, parameterized

The full Ana experience embeds with one URL — and the query parameters are your per-embed configuration surface:

<iframe
  src="https://app.textql.com/embed?authKey=MINTED_KEY_HASH&connectorIds=42,99&sqlEnabled=true&ontologyEnabled=true&pythonEnabled=false&webSearchEnabled=false"
  width="100%" height="600px" frameBorder="0" allow="clipboard-write">
</iframe>
Parameter groupParametersUse
Auth & sessionauthKey (the minted key hash from Module 1.3), chatId (resume a specific chat)Identity and continuity
Connector selectionconnectorIds=42,99 (comma-separated; takes precedence over legacy connectorId)Pin the embed to exactly its data
Tool togglessqlEnabled, ontologyEnabled, pythonEnabled, webSearchEnabled, googleDriveEnabled, tableauEnabled, powerbiEnabled — each true/falsePer-embed capability lockdown; omitted params fall back to org/role defaults

Notes that save debugging time: height of 500px+ (Ana's UI needs the room); allow="clipboard-write" so users can copy answers; the lockdown story is parameters + role together — the URL params shape the session, the key's role caps what's possible (params can't grant what the role denies).

4.2 · Where the iframe goes

Anywhere that hosts web content:

  • Your app — React/Vue/Angular component wrapping the iframe, src built server-side per session (never assemble auth params client-side)
  • Inside Tableau — a Web Page object on a dashboard pointed at the embed URL: Ana embedded next to the dashboards she can also analyze. There's also a one-click pattern for chats pre-attached to a specific Tableau collection: https://app.textql.com/tableau?authKey=...&tableauDatasetId=COLLECTION_ID&message=... (admins generate these links from the Attach Tableau flow; they run on a dedicated restricted Embed User key — rotate it from Settings → Developers if compromised)
  • Confluence / SharePoint / Retool / Appsmith — their respective HTML-embed or iframe components, same URL

4.3 · Embedding dashboards

TextQL dashboards (built and published per the Dashboards & Reporting workshop) embed two ways, by trust level:

PatternHowWhen
Authenticated viewThe dashboard inside the embed surface, viewer scoped by the minted key's role — RLS on the underlying connector applies automaticallyInternal portals; per-tenant views where the role/RLS does the scoping (Module 5)
Frozen artifactThe standalone interactive HTML report (Module 3.3) served from your storageExternal/customer surfaces where no live connection should exist

White-label depth (chrome removal, theming of the embedded surface) is deployment-dependent — org logo and report theming are configurable (Settings → Appearance), deeper UI customization varies by plan and deployment; confirm specifics with your TextQL contact before promising pixel-level branding in your product spec.

4.4 · Filters and refresh behavior

Two behaviors to design around rather than discover:

  • Filter passing: the embed URL pins connectors and tools, not dashboard filter state. For "this customer's view of the dashboard," the supported lever is identity — the minted key's role + connector RLS scope the data (Module 5) — not URL filter params. Design tenant scoping at the data layer, never as a client-side filter you hope holds.
  • Refresh: an embedded dashboard shows its last refresh, on the schedule its owner set — embedding doesn't change the cadence. State the cadence in your product UI ("Data as of …" from the dashboard's last-refresh time) so embedded staleness reads as designed, not broken.

Module 5

Module 5 · Multi-Tenant Patterns

⏱️ 20 minutes

Goal: the highest-stakes design decision for customer-facing embeds — how tenant A never sees tenant B, and what changes between 1 tenant and 100.

5.1 · The decision table

Three patterns, in increasing isolation and operational cost:

Shared connector + RLSConnector per tenantWorkspace per tenant
How isolation worksOne connector; row-level security in the warehouse filters by tenant, enforced by per-tenant identityEach tenant gets its own connector (own credential/schema/database); roles scope who reaches whichEach tenant is a separate TextQL organization
Blast radius of a mistakeOne missed RLS policy = cross-tenant leakOne mis-scoped role = one tenant pair affectedStructural — orgs don't share anything
Ops cost at N tenantsLowest — one connector, N policiesN connectors to create/rotate/monitor (automate via the connector APIs — Developer Workshop, Module 2)N orgs: provisioning, billing, ontology sync across all
Per-tenant ontology contextHard — shared context, tenant nuance via RLS onlyPossible — connector-scoped context per tenant connectorNatural — each org has its own ontology
FitsMany small tenants, uniform schema, strong warehouse RLS disciplineMid-market SaaS; tenants with schema variance or compliance wallsFew large enterprise tenants; regulated isolation requirements

5.2 · The scaling arc

What to do at 1 vs 100 is mostly when to automate, not which pattern:

  • 1–5 tenants: any pattern works hand-managed. Pick for your endgame, not your pilot — migrating isolation models with live tenants is the expensive path.
  • 5–50: the per-tenant pieces must be code: tenant onboarding = create connector (or policy), create role, map to your tenant registry — all scriptable through the management APIs.
  • 50+: shared-RLS economics usually dominate unless compliance forces isolation; your tenant-provisioning pipeline is now real infrastructure with its own tests (including the 5.4 negative test, per tenant, in CI).

5.3 · Wire identity to tenancy

Whatever the pattern, the chain is the same — and every link is server-side:

def embed_session_for(product_user):
    tenant = tenant_registry.lookup(product_user.tenant_id)
    # the minted key carries the tenant's role →
    # the role reaches only the tenant's connector(s) →
    # RLS (if shared pattern) filters rows by the tenant identity
    key = mint_scoped_key(roles=[tenant.textql_role_uuid], expiry=3600)
    return embed_url(authKey=key.hash, connectorIds=tenant.connector_ids)

The invariant to defend in review: tenancy is resolved from your authenticated user server-side, never from anything the client sends. A tenant_id in a request body is an attacker-controlled input; a tenant_id from your session is identity.

5.4 · The negative test is the deliverable

Per-tenant scoping you haven't adversarially tested is a hope, not a control:

PROMPT 
List every data source you can access. Then: what do you know about [tenant B's company name / a record ID belonging to tenant B]?
You'll see: only tenant A's connectors, and genuine unawareness of tenant B — not a refusal, unawareness. Run this both directions, plus the positive case (tenant A's own data answers correctly). Then automate it: this prompt pair, per tenant, is your tenancy regression suite — it runs in CI against minted keys, and it runs again every time a role, policy, or connector changes.

Module 6

Module 6 · Production Hardening

⏱️ 15 minutes

Goal: the gap between a working embed and a production feature: rate behavior, timeouts, cost controls, observability, and nondeterminism as a UX problem.

6.1 · Latency is the design constraint

Analytical answers take seconds-to-minutes, not milliseconds — your UX must be designed for that, not surprised by it:

  • Stream everything user-facing (Module 2) — perceived latency is the first token, not the last.
  • Status lines over spinners — "Querying your data… analyzing 3 tables…" reads as working; a 40-second blank spinner reads as broken.
  • Sync calls get minutes-scale timeouts and run server-side only; remember the platform's own ceilings (per-cell and per-query runtime limits) bound the longest possible wait — design the timeout budget around them, and use the cancel endpoint for user-abandoned runs.

6.2 · Cost controls

Every embedded question meters usage like any other chat — at product scale, this is a unit-economics line:

ControlImplementation
Cache identical questionsThe KPI-card case (Module 3.2): same question + same data freshness = served from cache with a TTL tied to the data's refresh cadence
Aggregate, don't loopOne question returning a table beats N questions returning numbers — design product features around table-shaped asks
Per-tenant budgetsMeter minted-key usage by tenant in your backend; throttle or upsell at thresholds you define
Watch the meterThe Usage API feeds your dashboards; alert on anomalies before the invoice does (admin-side detail: Admin & Governance, Module 4)

6.3 · Nondeterminism is a UX problem, not just a testing one

The same question can produce differently-worded (occasionally differently-approached) answers. Product patterns that absorb this gracefully:

  • Constrain where you need stability — JSON-shaped answers for programmatic surfaces (3.2), governed ontology definitions for the numbers themselves (so values are stable even when prose varies).
  • Fallbacks over retries for parse failures — if the JSON shape didn't come back, render the prose answer rather than burning a retry on the same ambiguity; retry (with backoff) only transport-level failures, and never blind-retry anything that writes.
  • An escape hatch on every answer — "wrong? ask again / refine" beats a support ticket; thread continuation (Module 2) makes refinement cheap.
  • Test contracts, not strings — response shape, asset presence, value-vs-golden checks (the Data Quality & Validation Deep-Dive pattern applied to your integration), never exact-string assertions.

6.4 · Observability for embedded usage

Log, per embedded interaction: your user/tenant, the chatId, latency to first token and to completion, parse outcomes, and the user's next action (refined? abandoned?). Two consumers: your product analytics (which embedded features earn their cost), and your support path — when a customer disputes an answer, the chatId links to the full thread with its inspectable SQL, which is the difference between "let me investigate" and an immediate, evidenced response. Admin-side, the Observability surface shows embedded threads alongside all others (admin access — Admin & Governance, Module 5).
