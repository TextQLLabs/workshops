POC in a Week

A 5-day guided evaluation structure for a customer data team and their champion running a TextQL proof of concept — with or without an FDE alongside. The modules are days, not topics: prerequisites the week before, connect and baseline Monday, ontology Tuesday, the question gauntlet Wednesday, automation Thursday, readout Friday.

The discipline that separates a real POC from a demo: success criteria written down before anything is connected, a cold baseline run honestly (misses included), and a warm re-run scored against it. The cold/warm gauntlet is the whole argument.

Who this is for

  • Customer data teams evaluating TextQL hands-on
  • Champions who need a defensible Friday readout, not a vibes-based one
  • FDEs running structured evaluations (the facilitator guide doubles as your run-of-show)

How to use this workshop

  1. Do Module 0 the week before. A POC that starts without written success criteria is a demo with extra steps.
  2. One module per day, in order. Each day's output is the next day's input.
  3. Swap [bracketed] placeholders for your systems, metrics, and team names.
  4. Keep everything — the baseline answers, the misses log, the scores. Friday's readout is assembled from the week's artifacts, not written fresh.
For facilitators — running this as a guided session

T-minus-1-day pre-flight: run the workshop's key prompts end-to-end in the session workspace — confirm logins, connectors, and the features this workshop touches are enabled for every attendee; have a fallback demo workspace ready in case a customer connector fails live. Pacing: when a long prompt is running (2–4 min), fire it first, then discuss the concept while Ana works — never watch a spinner in silence. If behind schedule, cut sections marked optional, never the checkpoints. Group sessions: attendees drive, you narrate; collect every miss or wrong answer in a shared doc — that list is the ontology backlog. With 10+ attendees on one warehouse, stagger the heavy prompts.

Module 0

Module 0 · Before Day 1: Prerequisites & Success Criteria

⏱️ 30 minutes, scheduled the week before Day 1

Goal: access secured, and — the most important artifact of the whole POC — real questions written down with their current time-to-answer, plus agreed success criteria.

0.1 · The access checklist

Chase these the week before; each missing item costs a half-day of the POC week:

  • [ ] Warehouse read-only credentials — a dedicated service identity, scoped to the schemas in play (the Connect Your Data workshop has per-warehouse specifics; share it with whoever provisions)
  • [ ] Network path cleared — IP allowlist or tunnel approved by security before Monday
  • [ ] Sample documents gathered — metric definitions, data dictionary, a few SOPs or wiki exports; messy is fine
  • [ ] Logins for every participant, tested
  • [ ] If access control is part of the evaluation: an admin login and a restricted test login

0.2 · The question list — the artifact that matters most

With the team (not alone), write down 5–10 real questions — ones someone actually asked in the last quarter, ideally ones that were painful to answer. For each, record the current reality:

#QuestionWho asks itCurrent time-to-answerCurrent path
1e.g., "Which customers' usage dropped >20% last quarter?"CS lead2 daysTicket to analytics → SQL → spreadsheet
2...

Rules for a good list: at least one question that spans two systems; at least one that hinges on a contested definition ("active customer," "qualified lead"); at least one that's genuinely hard. A list of softballs proves nothing on Friday.

0.3 · Success criteria — what does "won" look like?

Agree these with the economic buyer or champion in writing before anything is connected:

CriterionExample target
Questions answered correctly (warm run)≥ [7] of [9]
Time-to-answer improvementFrom days to ≤ [10 minutes] on at least [5] questions
Definition governance demonstratedThe [3] contested metrics governed and consistent
Automation demonstrated[1] playbook + [1] agent running on our data
Who judges correctness[Named person] checks against [named source]

Add your own rows — security review passed, a specific stakeholder convinced. The point is that Friday's verdict is scored against this table, not against impressions.

Module 1

Module 1 · Day 1: Connect & Validate

Goal: sources connected and validated, schema discovered — and the cold baseline run: every question asked with zero context, answers recorded honestly, misses included.

1.1 · Connect the warehouse and documents

Connect the warehouse with the Module 0 credentials (Connectors → New Connector; source-specific detail in the Connect Your Data workshop — including the smoke-test discipline). Upload the sample documents to the workspace.

PROMPT 
Pull the information schema for this connector. List the schemas and tables you can see, with approximate row counts where cheap. Flag anything that looks like a core entity (customers, orders, events) and anything you'd expect to see but can't.
You'll see: what Ana can actually reach — which is the credential's view. Anything missing is a grants problem to fix today, not Wednesday.

1.2 · The cold baseline — the honest run

Now run all 5–10 questions from Module 0, verbatim, with no ontology, no context documents attached to the thread, no coaching — just the raw connector. For each, record:

#QuestionCold answerCorrect? (judge: [named person])TimeNotes on the miss

Rules of honesty:

  • Ask each question once, as written. No rephrasing to help, no follow-up steering. (In real usage you'd converse — but the baseline measures the cold start, so resist.)
  • Record wrong answers and "I don't have that data" responses verbatim. Misses are the point — a baseline of all-correct answers means the question list was too soft (and means Day 3 can't show improvement).
  • The named judge from Module 0 scores correctness against the trusted source, today, while it's fresh.

For each question, paste it into a fresh message exactly as written:

PROMPT 
[Question #1 from your Day-0 list, pasted verbatim — no rephrasing, no added context]
You'll see: typically a mixed picture — some questions answered correctly off raw schema, some wrong on contested definitions (the cold run takes a definition, not your definition), some honest declines. Every miss goes in the misses log with a one-line cause hypothesis: definition gap / context gap / data gap / phrasing.

1.3 · End-of-day review

Fifteen minutes with the team: walk the baseline table. Set expectations explicitly: today measured the floor. Tomorrow adds the org's knowledge; Wednesday measures the difference. If anyone is disappointed today, remind them that a tool that aced contested-definition questions without being taught the definitions would be guessing — and guessing right is worse than asking.

Module 2

Module 2 · Day 2: Seed the Ontology

Goal: give Ana the org's knowledge — via a domain starter pack if one fits, or built from schema and documents — and govern the 3 most definition-sensitive metrics from the question list.

2.1 · Choose the seeding path

PathWhenHow
Domain starter packA pack matches your industry (the Healthcare Starter Pack is the canonical example)Load the pack, then adapt its definitions to your specifics — adaptation beats blank-page
Build from schema + documentsNo pack fitsThe discovery method from Build Your Ontology, End to End: Ana reads the schema and the Day-0 documents, drafts the model, you correct it

Either way, the input is what you gathered in Module 0: the documents, plus the schema Ana discovered on Day 1.

2.2 · Run the seeding

PROMPT 
Read the connected schema and the uploaded documents. Draft the ontology for this domain: the core entities and how they join, a business glossary from the documents, and the candidate metrics worth governing — flagging any metric where the documents and the schema suggest different definitions.
You'll see: a drafted model with definitional conflicts flagged. The flags are tomorrow's gold — most of Day 1's misses trace to exactly these.

2.3 · Govern the three that matter

From the question list, take the 3 most definition-sensitive metrics — the ones where Day 1's cold run picked a definition instead of your definition:

PROMPT 
Govern these three metrics: [metric 1] means [the org's definition — source, filters, edge cases]; [metric 2] means [...]; [metric 3] means [...]. Save them as governed definitions, and confirm by computing each for [last closed period] so we can check against [trusted source].
You'll see: the three definitions saved and computed — and the computed values checked against the trusted source today, by the judge. Governing a metric to the wrong value is worse than not governing it.

2.4 · Don't gold-plate

The temptation on Day 2 is to keep building — more entities, more notes, more polish. Stop at: entities mapped, glossary drafted, three metrics governed and verified. The POC tests whether the loop works (gaps found → knowledge added → answers improve), not whether a week can produce a complete ontology. Day 3's misses will tell you exactly what to add next; building speculatively today steals that signal.

Module 3

Module 3 · Day 3: The Question Gauntlet

Goal: re-run every question warm, score cold vs warm side by side, and turn the remaining misses into a prioritized backlog — fixing the quick ones live.

3.1 · The warm run

Same questions, same verbatim phrasing, same one-ask discipline — but now with the ontology attached. Extend the Day 1 table:

#QuestionCold answerWarm answerCold ✓/✗Warm ✓/✗Cold timeWarm time

The same judge scores the warm answers against the same trusted sources. Same rules: no steering, record verbatim.

PROMPT 
[Question #1 from your Day-0 list, pasted verbatim — identical phrasing to the cold run]
You'll see: the contested-definition questions flip to correct (they now route through your governed definitions), the cross-system question improve (the model knows the joins), and — usually — a couple of remaining misses. Good. A perfect warm run on a hard list happens; a perfect warm run on a soft list proves nothing.

3.2 · Score it

PROMPT 
Here's our gauntlet table [paste it]. Summarize: cold vs warm correct counts, average time-to-answer cold vs warm vs the original current-path times from our Day-0 list, and which question types improved most. Format as the scoring section of an evaluation readout.
You'll see: the POC's core evidence, computed from the week's own artifacts. This table — question, old time-to-answer, cold result, warm result — is the whole argument: not "the tool is impressive" but "the loop works: taught Tuesday, correct Wednesday."

3.3 · The misses log becomes the backlog

For each remaining miss, diagnose and sort:

Miss typeDiagnosisAction
Definition gapRouted through an ungoverned or wrong definitionQuick fix — govern it now, live (15 min)
Context gapA join, term, or business rule Ana wasn't taughtQuick fix if documented; backlog if it needs a human decision
Data gapThe data genuinely isn't in the connected sourcesHonest readout item — "answerable once [system] is connected"
PhrasingThe question is ambiguous even to a humanNote it — and show the conversational follow-up resolving it

Fix the quick ones live and re-run those questions. Watching a miss become a hit within the hour is the most persuasive moment of the week — it demonstrates the operating loop, which is what the customer is actually buying.

3.4 · The honesty principle

Carry the remaining misses into Friday's readout, labeled. An evaluation with documented misses and a working improvement loop is more credible than a flawless demo — every buyer has seen flawless demos, and knows what they're worth.

Module 4

Module 4 · Day 4: Automate & Wow

Goal: prove this is a platform, not a Q&A box — one playbook replacing a hand-built report, one feed agent watching the domain, one dashboard, and a role persona if access control matters to this evaluation.

4.1 · The playbook — replace a real report

Pick a report the team genuinely builds by hand today (the Day-0 conversation usually surfaced one). Build it as a playbook:

PROMPT 
Create a playbook "[their report name]" that runs [their actual cadence]: [the report's actual contents — metrics, comparisons, breakdowns, using the governed definitions]. Match the structure of the current report. If the period's data is incomplete, say so rather than reporting partials as final. Deliver to [their actual channel/email].
You'll see: their report, automated, on their definitions. Run it manually now and put the output next to the hand-built version — that side-by-side is a readout exhibit. (Prompt discipline and the 3-preview rule: Automation Deep-Dive.)

4.2 · The feed agent — watch their domain

PROMPT 
Create a feed agent "[Domain] Watch" that checks [their data] daily and posts ONLY when something material changes: [2–3 thresholds from their domain — a metric moving >X%, a new top-N entity, an anomaly]. One paragraph with the evidence. Silent otherwise.
You'll see: the agent deployed. It likely won't fire before Friday — say that in the readout and show the configuration instead; an exception-only watcher that stayed correctly silent for two days is the feature working.

4.3 · The dashboard

PROMPT 
Build a dashboard for [the domain]: a KPI row using our three governed metrics with period-over-period deltas, the main trend chart, a breakdown table, and filters for [date range] and [their key dimension]. Default to [last closed period].
You'll see: a live dashboard on governed definitions (depending on workspace configuration, an admin may need to enable Dashboards). Verify the headline KPI against the trusted source before showing anyone — Day 5 demos only verified numbers. (Craft: Dashboards & Reporting.)

4.4 · The role persona (if access control is in the evaluation)

With the restricted test login from Module 0:

PROMPT 
What data sources can I access, and what do you know about [a metric/folder the restricted role shouldn't see]?
You'll see: the restricted view — scoped connectors, and genuine unawareness of restricted context rather than a declined request. Then ask something the role should see and confirm it works. Both directions, witnessed by the security stakeholder if there is one. (Full model: Admin & Governance.)

4.5 · Stage Friday

End the day by assembling the demo path: the gauntlet table, one live warm question, the playbook side-by-side, the dashboard, the agent config, the persona flip. Dry-run it once — 15 minutes, no surprises.

Module 5

Module 5 · Day 5: The Readout

Goal: score the week against the Day-0 criteria, deliver the before/after table, run a 15-minute exec demo on their data and their questions, and leave with a decision and a rollout sketch.

5.1 · Score against Day 0 — first, and in their words

Open the readout with the success-criteria table from Module 0, scored row by row:

Criterion (agreed Day 0)TargetResultMet?
Questions correct (warm)≥ 7/9[8/9]✓
Time-to-answer≤ 10 min on 5+[9 of 9 under 5 min]✓
...

This is why Module 0 insisted on writing them down: the verdict is a comparison against pre-agreed targets, not a negotiation about impressions.

5.2 · The before/after table

The week's centerpiece exhibit, one row per question:

QuestionOld time-to-answerNew (warm)Correct?Definition governed?
PROMPT 
Assemble the readout pack: the success-criteria scorecard, the before/after question table, the cold-vs-warm summary from Day 3, the remaining misses with their diagnoses and what each needs, and the automation inventory from Day 4. Executive summary up front — findings, not feature descriptions. PDF.
You'll see: the readout assembled from the week's own artifacts. The misses section stays in — labeled, diagnosed, with the fix path. Honest misses next to a working improvement loop is the credibility play; a misses-free readout reads like marketing.

5.3 · The 15-minute exec demo

Their data, their questions, this script:

MinutesBeat
0–2The Day-0 question list and what answers used to cost (the before column)
2–6Live: two questions from the gauntlet, asked warm — one number, one "why" — with "how did you calculate that?" on the second
6–9The playbook side-by-side: the hand-built report vs the automated one
9–11The dashboard; if access control matters, the 30-second persona flip
11–13The honest slide: what missed, why, and the Tuesday-taught-Wednesday-correct loop that fixes it
13–15The scorecard, and the ask: production rollout

Live questions only from the warm gauntlet — verified answers, no first-time prompts in front of executives.

5.4 · What production rollout looks like

Close with the sketch, not a vague "next steps":

  1. Data: production credentials and remaining sources (Connect Your Data); the data-gap misses name the priorities
  2. Knowledge: the misses backlog becomes the ontology roadmap (Build Your Ontology → Ontology Operations for the operating loop); golden tests pin the governed metrics (Data Quality & Validation Deep-Dive)
  3. People: identity, roles, and access (Admin & Governance); then user enablement by population (Self-Service Analytics for business users, the vertical workshops where they fit)
  4. Rhythm: the Day-4 automations move to production cadence (Automation Deep-Dive)
